# 看见其他玩家与真人组队（设计）

状态：**第一节已实现（STAGE-273）**；第二节（真人组队）仍是**设计草案**（2026-10-22）。这份文档先把规则、协议草案和界面定下来；落地时按末尾的拆单顺序做，规则并入 `protocol.md`、`ui.md`、`interaction.md`，本文随后只保留设计依据。

**说人话**：现在进了世界只有自己和 NPC，别的玩家完全看不见。要做两件事：

1. 场景页多一列「附近玩家」，放在 NPC 和遇敌之间，能看到同一张地图上有谁、选中他可以看资料或邀请组队。
2. 真人组队：邀请、申请加入、离队、队长踢人。队伍里的人一起换图、一起打架。

## 现状（设计依据）

| 方面 | 现状 | 对设计的影响 |
|---|---|---|
| 玩家之间 | 完全不可见；只有同账号的玩家连接与 agent 连接互相同步（`protocol.md` 9.5 的“公开发言”也只是预留） | 需要一份“同图在线角色”索引 |
| 服务端存在感 | 每个在世界里的角色是一个 `Presence`（`server/character/world.go`），只在内存；连接统一由 `gateway.Hub` 管，`npcs_changed` 已经是“按地图推送” | 复用同样的按地图推送；新增 `floor → Presence` 索引 |
| 队伍 | 只有分身队（`protocol.md` 5.57，STAGE-162）：队长 + 4 个分身，存在队长 `Presence.party` 里；文档明写“分身不能被邀请、不做真人组队” | 真人队是 `party.kind = players`，与分身队**互斥** |
| 战斗 | `battle.Battle` 只有一个真人（`You`、`sides[2]` 一方一份快照）；协议已为多人留了口子（`battle_progress` 的“等待其他玩家 2/3”、`kind` 追加取值） | **真人同场战斗要改引擎**，是独立的大块，单独成单 |
| 移动 | 没有手动走路，换位置只有传送 / 出口（`cli-ui-redesign.md`） | “附近”只能按**同一张地图**算，不做坐标距离；队伍“跟随”靠服务端同步位置 |
| 角色名 | 全服唯一（`NAME_TAKEN`） | 协议里直接用角色名定位玩家，不另造编号 |
| 场景页 | 三列：出口 / NPC / 遇敌（STAGE-152，`ui.md`、`interaction.md`） | 改成四列：出口 / NPC / **玩家** / 遇敌 |
| 社交页 | 只有「队伍」一栏，无队伍时 Enter 直接组分身队 | 队伍栏要兼容真人队，新增「请求」栏 |

## 一、附近玩家（看见其他玩家）

### 1.1 规则

- **“附近” = 同一张地图**（同 `floor`）。不显示距离、不显示坐标，避免让人以为可以走过去。
- **谁出现**：同图、已进入世界的其他角色。不含自己，也不含自己的分身。agent 操控中的角色照常出现（对其他玩家来说就是那个角色，`protocol.md` 9.5）。
- **能看到什么**（只给这些，别的一律不给）：

  | 字段 | 说明 |
  |---|---|
  | `name` | 角色名，也是后续邀请等请求的目标标识 |
  | `level`、`transmigration`、`title` | 等级、转生次数、称号 |
  | `in_battle` | 是否战斗中 |
  | `party` | 所在队伍摘要：`{"leader": "队长名", "size": 3, "max": 5, "kind": "players"}`，没有队伍为 `null`；分身队**不对外显示**（对别人来说他就是单人） |

  不给：账号名、HP/MP、石币、装备、宠物、背包、任务。这些在队伍内部才可见（见 2.7）。
- **上限**：一次最多返回 50 人，超出时 `truncated: true`，列表底部写「还有更多玩家未显示」。排序：队长/有队伍的在前，其次等级高到低，再按名字。
- **可见性开关**（第二批，见第三节）：玩家可以关闭「对附近玩家可见」，关闭后不出现在别人列表里，自己仍能看到别人。

### 1.2 协议草案

查看类，世界中，玩家和 agent 都能发；观察方也能查看。

```jsonc
{"id": 80, "type": "players", "data": {}}
{"id": 80, "type": "players", "ok": true, "data": {"floor": 1000, "truncated": false, "players": [
  {"name": "小红", "level": 12, "transmigration": 0, "title": "", "in_battle": false,
   "party": {"leader": "阿牛", "size": 3, "max": 5, "kind": "players"}},
  {"name": "阿牛", "level": 30, "transmigration": 1, "title": "勇者", "in_battle": true, "party": null}
]}}
```

推送 `players_changed`：推给**这张地图上所有在世界中的连接**（玩家和 agent，规则同 `npcs_changed`），增量而非整表，因为人进进出出频繁：

```jsonc
{"type": "players_changed", "data": {"floor": 1000, "changes": [
  {"op": "enter",  "player": {"name": "小明", "level": 5, "...": "同上"}},
  {"op": "update", "player": {"name": "阿牛", "in_battle": false, "...": "整条替换"}},
  {"op": "leave",  "name": "小红"}
]}}
```

- 触发：进入世界 / 离开世界 / 断线（`leave`）；换图（旧图 `leave`、新图 `enter`，紧跟 `position_changed`）；升级、转生、改称号、加入或离开队伍、战斗开始或结束（`update`）。
- **合并发送**：同一张地图的变更攒 1 秒再发一次（一条推送带多项 `changes`），免得“无限遇敌”的玩家每场战斗刷屏；一个玩家在窗口内多次变化只留最后一条。
- 客户端按 `name` 应用增量；不认识的 `op` 忽略；重连、换图后以一次 `players` 的整表为准（推送丢失不影响正确性）。
- 服务端实现：`World` 增 `byFloor map[int64]map[int64]*Presence`（charID），在进入/离开世界和位置变化处维护；推送沿用 `Hub.Publish` 的“键”（键为地图）。

### 1.3 场景页：第四列

四列顺序：**出口 / NPC / 附近玩家 / 遇敌**。

```text
┌ 出口 ────┐┌ NPC ─────┐┌ 附近玩家 3 ┐┌ 遇敌区域 ────┐
│ ▶ 村长家 ││ 村长     ││ ★阿牛  L30 ⚔││ #12 野猪 L3  │
│   北门   ││ 商店     ││ ·小红  L12 ││ #13 土狼 L5  │
│          ││ 护士     ││   小明  L5 ││ 停止遇敌     │
└──────────┘└──────────┘└────────────┘└──────────────┘
```

- **行格式**：`标记 名字 Lv`。标记一个字符：`★` 队长、`·` 队员、空白 无队伍；战斗中行尾加 `⚔`（灰色）。`--unicode false` 时改 ASCII：`*`、`-`、`!`。名字过长按终端宽度截断，等级必须保留。
- **颜色**（16 色具名）：普通 White，有队伍 Yellow，战斗中 DarkGray；标题 `附近玩家 N`，焦点时加 `*` 并加粗，规则同其他三列。
- **宽度**：用 `Constraint::Percentage(24/26/22/28)`；80×24 时玩家列内宽约 16 格，容纳“5 个汉字的名字 + Lv12”。再窄（< 80）不在设计范围内。验收必须在 80×24 跑一遍。
- **按键**（与 `interaction.md` 一致）：`←→` 在四列间切、到两端停住；`↑↓`、`Home/End`、`PgUp/PgDn` 只管当前列，四列各记选择与滚动位置；`Tab` 打开详情；`F5` 刷新焦点列。
- **Enter**：弹出动作面板（同遇敌列的面板，`Esc` 关闭、默认选第一项）：

  | 动作 | 条件 |
  |---|---|
  | 查看资料 | 总是 |
  | 邀请组队 | 自己没有队伍或自己是队长，对方没有队伍、不在战斗中、队伍未满 |
  | 申请加入 | 对方是队伍的队长，队伍未满，自己没有队伍 |
  | 请出队伍 | 自己是队长，对方是自己队员 |
  | 取消 | 总是 |

  不满足条件的动作仍显示但灰掉，`Enter` 只在消息栏说明原因，不发请求。
- **详情（Tab）**：名字、称号、Lv、转生次数、队伍（队长名、人数）、是否战斗中。
- **状态**：「加载中…」「加载失败：原因（F5 重试）」「本图没有其他玩家」三种分别显示，不能把失败冒充成空列表。进入世界、换图、重连刷新时与出口、NPC 一起拉取；请求按响应 id、地图、连接世代隔离，旧响应不能覆盖当前地图（同 STAGE-148/152 的做法）。
- **观察方**（agent 操控时的玩家连接）：列表可看、详情可看，邀请 / 申请 / 请出队伍灰掉并提示“agent 正在操控，输入 take 收回控制权”。

### 1.4 命令

`/players` 把焦点切到场景页的玩家列并刷新；不单独做命令行文字版列表。需要指名操作时直接用组队命令（见 2.8）。

## 二、真人组队

> **状态（STAGE-274）**：协议与用例已定（`docs/protocol.md` 5.67，`docs/protocol/cases/party_players_*`），服务端与客户端待实现；2.6 战斗归 STAGE-275。

### 2.1 规则一览

| 规则 | 说明 |
|---|---|
| 人数 | 一队最多 5 个真人 |
| 种类 | `party.kind` 取 `clone`（分身队）或 `players`（真人队），**互斥**：有分身队时不能邀请，也不能被邀请；想组真人队先解散分身队。真人队里不能再加分身 |
| 队长 | 谁邀请成功，谁就是队长；队长离队时按入队先后顺位接任；只剩 1 人时队伍解散。战斗中队长掉线、超时、逃跑成功都是**解散**，不接任（见 2.6） |
| 邀请 / 申请 | 邀请：队长（或还没有队伍的人）→ 对方；申请：没有队伍的人 → 对方队长。**只有同图才能发**；对方答应时可能已不同图，见 2.4 |
| 谁能邀请 | 无队伍者和队长；队员不能邀请（`NOT_PARTY_LEADER`） |
| 踢人 | 只有队长，只能踢队员；被踢的人留在原地，队伍里其他人不受影响 |
| 战斗中 | 队伍正在战斗时，不能邀请、加入、主动离队、踢人、解散（`PARTY_IN_BATTLE`）。例外：战斗中**逃跑成功**、**超时被踢出**、**掉线**，成员会离队（队长则解散全队），见 2.6 |
| 跟随 | 队员**不能自己换图**，位置永远跟着队长（见 2.5） |
| 断线 | 成员的所有连接都断开 = 离队（不保留座位，重登要重新入队）；同账号 agent 连接还在线不算断开（与分身队一致） |

### 2.2 邀请与申请的流程

```text
队长A  ──party_invite{name:B}──▶ 服务端 ──push party_request──▶ B
                                   │◀── party_reply{id, accept}───┘
A、B   ◀──push party_changed / party_request_result──┘
```

统一用“请求”对象表示邀请和申请：

```jsonc
{"id": "r-17", "kind": "invite",          // invite（邀请你加入我的队伍）或 apply（申请加入你的队伍）
 "from": "阿牛", "party": {"leader": "阿牛", "size": 2, "max": 5}, "expires_in": 30}
```

- **有效期 30 秒**，到期自动作废，发起方收到 `expired`。同一对 (发起人, 对象) 同时只能有一条待处理请求，重复发送回复 `REQUEST_PENDING`；每个玩家最多同时收 5 条，满了发来的回复 `TARGET_BUSY`。同一发起人对同一对象 10 秒内最多发一次，超了回复 `RATE_LIMITED`（带 `retry_after_seconds`）。
- **发起校验顺序**：控制权 → 自己倒下 → 自己战斗中 → 目标存在且同图（`PLAYER_NOT_NEARBY`）→ 目标不是自己（`INVALID_TARGET`）→ 目标拒绝邀请（`TARGET_REFUSES`，见 protocol 5.69）→ 目标战斗中（`TARGET_IN_BATTLE`）→ 目标已有队伍（`TARGET_IN_PARTY`）→ 自己队伍已满（`PARTY_FULL`）→ 自己是队员（`NOT_PARTY_LEADER`）→ 自己有分身队（`ALREADY_IN_PARTY`）→ 频率。
- **答复**：`party_reply {id, accept: true|false}`。接受时服务端**重新校验**一次：请求还在、发起方还在线且仍是队长（或仍无队伍）、队伍没满、答复者仍无队伍、双方都不在战斗中。不满足回复对应错误码，请求作废。
- **邀请的发起人还没有队伍**：接受的那一刻才建队，发起人成为队长，答复者是第二个成员。申请同理：对方还没有队伍时不允许申请（`TARGET_NOT_LEADER`，申请只对已有队伍的队长发；想组队就用邀请）。
- 对方拒绝或忽略：发起方收到 `party_request_result`（`declined` / `expired` / `cancelled` 等），不在消息里透露拒绝原因。
- `party_cancel {id}`：发起方撤回自己发出的待处理请求。

### 2.3 离队、踢人、解散

| 操作 | 请求 | 谁 | 结果 |
|---|---|---|---|
| 离队 | `party_leave` | 任何成员（含队长） | 队长离队则顺位接任（`leader_changed`）；剩 1 人则队伍解散；战斗中回复 `PARTY_IN_BATTLE`（见 2.1） |
| 踢人 | `party_kick {name}` | 队长 | 目标收到 `kicked`（`party` 为 `null`），其余人收到 `member_kicked`；不能踢自己（`INVALID_TARGET`）、不是队员（`NOT_PARTY_MEMBER`） |
| 转让队长 | `party_leader {name}` | 队长 | 全队收到 `party_changed`（`leader_changed`，`who` 为新队长）；新队长排到 index 0，原队长排到第 1 位；不能转给自己（`INVALID_TARGET`）、不是队员（`NOT_PARTY_MEMBER`）（STAGE-277） |
| 解散 | `party_disband`（沿用） | 队长 | 全体收到 `disbanded`；分身队的行为不变 |

被踢、被解散、自己离队的人留在**当前地图**，不传送。被踢的人不被拉黑，队长可以再邀请他。

### 2.4 加入时的位置

接受邀请 / 申请时，若答复者与队长不在同一张地图：服务端把**答复者传送到队长的位置**（走与队伍跟随相同的路径），推 `position_changed` 与 `players_changed`。答复者正开着 NPC 窗口则先发 `npc_window_closed`。理由：不走路的游戏里“同图”只是条件，不应该因为邀请发出后有人动了一步就让接受失败。

### 2.5 跟随

- 队长的 `warp`、`use_exit`、NPC 传送、`encounter_start` 与 `pet_encounter_start`、战败回城等任何位置变化，成员的位置同步到队长新位置，成员连接收到 `position_changed`（`reason: "follow"`）并紧跟 `party_changed`（`moved`，沿用 5.57）。同步前成员的 NPC 窗口先关闭（`npc_window_closed`）。
- 队伍战斗中位置不会变（2.1 战斗中不能变更，队长也在战斗里不能传送）；个别成员因重连等原因此刻不在战斗中而队伍在战斗中的，等战斗结束再同步。
- **队员自己的换图类请求**——`warp`、`use_exit`、`encounter_start`、`pet_encounter_start`、`encounter on`、传送员 NPC——一律回复 `PARTY_FOLLOWER`，说明“跟随队长，离队后才能自己行动”。队员仍可以对话、买卖、用道具、整理背包、查任务等原地操作。
- 队员客户端的灰显：场景页出口列、固定的「传送到其他地点」「回城」、遇敌列、快捷传送页的“传送”动作都灰掉并带原因。

### 2.6 战斗（真人同场）

真人同场战斗需要战斗引擎支持多真人，是独立的大块（拆单见第三节）。**规则以原版 2.5 为准**：调研结论与源码行号见 `docs/battle-party-research.md`，这里只写协议和服务端必须遵守的约束。标“开工核对”的是调研里未查实的项，开工前先看原版对应行再定。

- **谁触发、谁同场**：队长的遇敌（或战斗 NPC 对话）开战时，全体在线队员同场；队员不能自己遇敌（2.5）。开战后不能中途加入（2.1）。
- **站位**：队长先入，其余队员按入队先后占己方 0–4 号；宠物号 = 主人号 + 5（5–9）。`battle_start.you` 每人不同。
- **`battle_start.kind`**：真人队同场的战斗取新值 `party`（野外遇敌或战斗 NPC 都是；NPC 的 `npc` 对象照带）。单人战斗仍是 `wild` / `npc`，分身队战斗不变。
- **出招**：每人各交自己的人物和宠物指令（`battle_turn.needs` 只针对该角色）。回合结算等**所有仍在战斗中的真人**交齐（原版 `BATTLE_CommandWait`）。进度 `done/total`：total 是本回合需要交指令的真人数，done 是其中已交齐的人数；界面显示“等待其他玩家 done/total”（`docs/battle-ui.md`）。
- **120 秒超时**：本回合第一条被接受的 `battle_command` 起计时 120 秒。到点仍没交齐的真人被踢出战斗并离队（原版 `battle.c:2839-2853`）。**没有默认指令**，原先“按超时默认指令处理”的写法作废。超时的人宠物随之退场，其余人继续打；超时的是队长则全队解散，其余队员留在战斗里。
- **整场 3600 秒**：超过战斗时限（原版 `BATTLE_TIME_LIMIT`），仍在战斗中的真人都以 `draw` 结束（开工核对：原版只退场仍在等指令的人，见报告第 4 节）。
- **逃跑是个人行为**：按原版 `BATTLE_Escape` / `BATTLE_EscapeCheck`，成功只让自己和自己的宠物退场，并**离开队伍**；队长逃跑成功则全队解散，其余队员留在战斗里。成功率照原版公式，**没有队伍因素**；失败只累计该格的逃跑次数。
- **掉线**：立即退场，不结算经验、战利品、金钱；宠物随之退场；血量照存（人物倒下则回 1）；立即离队。队长掉线则全队解散，**不顺位接任**。其余人继续战斗。
- **胜负**：己方败 = 己方没有存活的**非宠物**玩家（分身不算，STAGE-169）；敌方全灭、被捕获或逃走（同 10.9 的 `win` 规则）则己方胜。
- **结算**（每人各收一条 `battle_end`，只含本人份额）：
  - 经验：只给出手者；组合技给组合成员；队员没出手拿 0。等级差折算、骑宠 60% 按原版。宠物经验是否重复结算：**开工核对 `battle.c:3189-3200`**。
  - 掉落：每件道具在击倒时随机分给本次出手列表中的**一人**（不是每人独立掷）；分到的人战斗结束时已死亡，拿不到。死亡玩家已分得的道具是否回收，开工核对。
  - 金钱：调研未查实，开工核对 `BATTLE_GetExpGold` 的金钱段；暂定只给存活的真人。
  - 忠诚、装备耐久：各自结算（宠物的忠诚归其主人，耐久归使用者）。
  - 捕捉：归出手的成员，宠物入其宠位。
  - 失败：每个倒下的真人按自己的情况处理（原地复活或被打飞，见 10.9），魅力、金钱、经验损失各算各的。
- **敌群数量**：默认不随人数变化；开工时读遇敌表核对（调研未查实）。
- **分身队**：战斗行为不变；真人队里没有分身。

### 2.7 队伍对象（真人队）

沿用 5.57 的 `party` 结构，`kind` 取 `players`，成员条目**少给**：

```jsonc
{"kind": "players", "leader": "阿牛", "members": [
  {"index": 0, "name": "阿牛", "leader": true,  "clone": false, "online": true,
   "level": 30, "hp": 400, "max_hp": 400, "mp": 90, "max_mp": 90,
   "pet": {"name": "乌力", "level": 20, "hp": 120, "max_hp": 150},
   "position": {"floor": 1000, "map_name": "萨姆吉尔村"}}
]}
```

- 不给队员的属性、装备、精灵、宠物技能（`stats`、`derived`、`equipment`、`magic`、`pet.skills`），这些只有分身队才有（那是自己的数据）。队友能看到的只是组队界面必要的血蓝。
- `index` 在成员离队前稳定；客户端用 `name` 保持选中，不用 `index`。
- `position` 里不给坐标，因为全员与队长一致。
- 新增的 `party_changed.reason`：`member_joined`、`member_left`、`member_kicked`、`kicked`（给被踢者，`party` 为 `null`）、`left`（给离队者，`party` 为 `null`）、`leader_changed`；每条另带 `who`（涉及的角色名）。其余沿用 `created`、`disbanded`、`moved`、`battle_end`。
- `enter_world` 和 `status` 的 `party` 字段对真人队同样有效，重连后以它为准；重连后若已被移出队伍则是 `null`。

### 2.8 界面

**收到邀请 / 申请**：任意页面上方弹一个居中的确认窗口（场景、菜单、功能页都弹；战斗中和 NPC 对话窗口里**不弹**，只在消息栏提示，战斗结束或关窗后若请求还没过期再弹）：

```text
┌ 组队邀请 ───────────────────┐
│ 阿牛 邀请你加入队伍（2/5）  │
│ 剩余 23 秒                  │
│       [拒绝]    [加入]      │
└─────────────────────────────┘
```

- 按钮遵守“默认取消”：焦点默认在「拒绝」，`←→` 切，`Enter` 激活；`Esc` = **稍后处理**（收起窗口，请求保留到过期）。这与确认类窗口的“Esc 取消”一致，因为取消的是“现在决定”这个动作，不是回答。
- 倒计时每个 tick 刷新；过期自动关闭并在消息栏写「阿牛的组队邀请已过期」。
- 同时有多条请求时按先后排队，一次弹一条。

**社交页**（`Esc` 菜单 → 社交）：栏目 `←→` 切换，现在是「队伍」和「请求」两个：

- **队伍**：真人队是成员表（沿用分身队的表：标出队长，每行 HP 条，宽屏右侧详情只显示 2.7 里有的字段）。`Enter` 选中成员后的动作：

  | 选中 | 动作 |
  |---|---|
  | 自己（非队长） | 离开队伍（默认取消的确认） |
  | 自己（队长） | 解散队伍（默认取消的确认） |
  | 队员（自己是队长） | 查看详情、请出队伍（默认取消的确认） |
  | 队员（自己是队员） | 查看详情 |

  没有队伍时 `Enter` 打开两项：「组成分身队」（沿用，无损失不二次确认）和「去邀请附近玩家」（回场景并把焦点放到玩家列）。
- **请求**：收到的邀请 / 申请（可答复）和自己发出、等待答复的请求（可撤回），每条带倒计时；`Enter` 对收到的请求打开同样的加入 / 拒绝窗口，对发出的请求给「撤回」。没有请求时写「没有待处理的组队请求」。

**消息栏**：队伍类消息沿用（Green），新增内容：阿牛邀请了你；小红加入了队伍；小红离开了队伍；小红被请出了队伍；队长换成了小红；你被请出了队伍；邀请被拒绝 / 已过期。

**命令**（菜单与命令共用同一批函数，`client/src/app/party.rs`）：

| 命令 | 别名 | 含义 |
|---|---|---|
| `party` | `队伍` | 打开社交页（已有） |
| `party invite 名字` | `邀请` | 邀请 |
| `party join 名字` | `加入` | 向对方队长申请 |
| `party accept [名字]` | `同意` | 同意收到的请求；不带名字时取最早的一条，多条时必须带名字 |
| `party decline [名字]` | `拒绝` | 拒绝 |
| `party leave` | `离队` | 离队，先确认（默认取消），`leave yes` 直接离 |
| `party kick 名字` | `踢` | 请出队员，先确认，`kick 名字 yes` 直接踢 |
| `party clone` / `party disband` | | 已有，不变 |

### 2.9 agent

- 新请求是操作类，agent 操控、玩家观察时玩家连接被拦；`players` 是查看类，两边都能发。
- `docs/agent-guide.md` 第 6 节的先问分级（`go test ./server/webpages` 会检查，漏了就失败）：

  | 级别 | 请求 |
  |---|---|
  | 第一级 | `party_reply` 的拒绝、`party_cancel` |
  | 第二级 | `party_invite`、`party_join`（申请）、`party_leave` |
  | 第三级（必须先问） | `party_reply` 接受（会改变位置并绑定行动）、`party_kick`（影响别的真人）、真人队的 `party_disband`、`party_leader`（转让队长） |

### 2.10 错误码

| 错误码 | 含义 |
|---|---|
| `PLAYER_NOT_FOUND` | 没有这个在线角色 |
| `PLAYER_NOT_NEARBY` | 不在同一张地图 |
| `TARGET_IN_BATTLE` | 对方在战斗中 |
| `TARGET_IN_PARTY` | 对方已有队伍 |
| `TARGET_NOT_LEADER` | 申请的对象不是队长 |
| `TARGET_BUSY` | 对方待处理的请求已满 |
| `TARGET_REFUSES` | 对方关闭了“接收组队邀请”（STAGE-276 起返回，见 protocol 5.69） |
| `PARTY_FULL` | 队伍已满 5 人 |
| `NOT_PARTY_LEADER` | 需要队长身份 |
| `NOT_PARTY_MEMBER` | 目标不是队员 |
| `PARTY_IN_BATTLE` | 队伍战斗中不能变更 |
| `PARTY_FOLLOWER` | 队员不能自己换图、遇敌 |
| `REQUEST_NOT_FOUND` | 请求不存在或已过期 |
| `REQUEST_PENDING` | 已有一条待处理的同类请求 |

### 2.11 服务端实现要点

- 真人队是一个**独立的共享对象**（`partyState` 现在挂在单个 `Presence` 上，不够用），自己带锁，成员的 `Presence` 持有它的指针；分身队保持原样。
- **锁顺序**：`World` 索引 → 队伍锁 → 各 `Presence.mu`（多个成员时按 `charID` 升序）。跟随、踢人、解散都是“持队伍锁、逐个锁成员”，不允许反过来。
- 请求表放在 `World` 上，键是 `(发起人, 对象)`，到期用单个定时器扫描，不为每条请求建 `time.Timer`。
- 位置变化统一走一个“成员跟随”钩子，挂在已有的 `position_changed` 发出点后面（分身队的 `moved` 就在那里），不要在每个换图入口各写一遍。
- 不落库：队伍、请求都只在内存，服务重启全部消失。这是第一期的有意取舍，和分身队一致。
- 协议用例需要**两个账号同时在线**。开工前先确认 `server/casetest` 的用例格式能否表达两条玩家连接（现有 `party_agent` 是玩家 + agent 两条，参考它）；不能就先扩测试客户端，再写用例。

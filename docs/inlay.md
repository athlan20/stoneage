# 精工（镶宝石）设计

STAGE-232（设计已定稿，开发见 STAGE-297/298/299）。把“精工”按原版逐行对照写清楚：入口、规则、台词、数据、对新服务端的影响，以及要拍板的几件事。依据是原版服务端 `original-data/gmsv`（只读，下称 gmsv/），GBK 注释已转 UTF-8 读取。`docs/magic-acquire.md` 第 2.3 节和第六节第 4 条是 STAGE-204 的研究结论，**本文核对后有三处要更正**（见第一节）。

## 0. 结论摘要

1. **精工不只是“覆盖精灵”**：镶一件材料，武器/防具会**累加**材料的攻、防、敏、HP、MP、运气、伤、吸，**覆盖**魔法 ID 与 MP（材料有魔法时），**替换**物品的各个函数和参数，并**重写效果文字**。同时登记一个镶嵌格，一件武器防具**一共只有 3 格，镶了就不可恢复**。
2. **“一次最多 4 件”是 4 件物品，包含那件武器/防具**，也就是 1 件装备 + 最多 3 件材料，正好填满 3 格。STAGE-204 文档和 STAGE-232 描述里写的“最多 4 件材料”是错的。
3. **原版的数据是死的**：`itemset.txt` 第 4、5 列（`acode`、`inlaycode`）12620 行全空，没有任何物品被标成“可镶装备”或“可作材料”；`petskill.txt` 里没有精工技能；类型 22（宝石）一个也没有，类型 21（金属）只有一件“燃烧的火把”；伤、吸两个字段（第 32、33 列）也全空。**也就是说，原版代码完整，但 2.5 的数据没有启用它**，按原版数据走，任何物品放进去都只会得到“这样物品不适合精工。”。
4. **新服务端要做的不只是一个请求**：装备的数值现在只按物品编号查模板（`equip_rules.go` 的 `equipBonus`），没有“这件物品自己的加成”，精工需要给物品行加一份**实例级覆盖**（加成、魔法、效果文字、镶嵌格）。
5. **推荐做法**：机制按原版做到位、数据驱动；数据保持原版（功能默认休眠），另给一份可选的覆盖表，让运营要启用时不必改 `itemset.txt`。入口用一个专门的请求 `item_inlay`，不借宠物技能（数据里没有这条宠物技能）。

## 一、原版怎么做

### 1.1 入口

- 注册：`battle/pet_skill.c:53-54`（`#ifdef _ITEM_INSLAY`，`{"PETSKILL_Inslay", PETSKILL_Inslay, 0}`），`_ITEM_INSLAY` 在 `include/version.h:144` 打开。
- 链路：客户端 PS 请求 → `callfromcli.c:1621-1632` `lssproto_PS_recv` → `pet_skill.c:505` `PETSKILL_Use`，按宠物技能编号查 `petskill.txt` 的函数名列，再调函数指针 → `PETSKILL_Inslay`（`pet_skill.c:1546`）。
- `petskill.txt`（32 行）**没有任何一行**引用 `PETSKILL_Inslay`；精工在 2.5 的宠物没有这个技能可学。`include/pet_skillinfo.h:80` 里也只有声明。客户端不在本仓库，哪个按钮发的 PS 没法核对。
- 客户端提示：`item/item.c:1296-1303` 发给客户端的物品标志里，类型 21（`ITEM_METAL`）置第 3 位、类型 22（`ITEM_JEWEL`）置第 4 位，应该是客户端用来筛“能当材料的物品”的提示。服务端不看这两位，判定只看 `ITEM_TYPECODE`（见 1.2）。

### 1.2 数据字段

| 字段 | 位置 | 含义 |
|---|---|---|
| `ITEM_TYPECODE`（`acode`） | `itemset.txt` 第 4 列（字符列顺序 `na, sn, en, ar, acode, inlaycode, …`，`item.c:105-107`） | 物品的“精工类别码”。**含子串 `INSLAY`** = 是可以镶东西的武器/防具；**其他非空且不是 `NULL`** = 可以当材料；空或 `NULL` = 不适合精工 |
| `ITEM_INLAYCODE`（`inlaycode`） | 第 5 列 | 武器/防具身上已经镶了什么，格式 `码1\|码2\|码3`，空位写 `NULL`。除了 `PETSKILL_ITEM_inslay` 自己，**全部源码没有任何地方读它**，所以它的作用只是“记录占了几格” |
| `ITEM_OTHERDAMAGE` / `ITEM_OTHERDEFC` | 第 32、33 列（“伤”“吸”） | 额外伤害、额外防护。战斗里在伤害公式末尾加上 `RAND(伤×0.3, 伤) − RAND(吸×0.3, 吸)`，不为负（`battle/battle_event.c:1119-1130`）；穿戴时的累计范围 −100 到 100（`item/item.c:1412-1413`） |

### 1.3 `PETSKILL_Inslay`（`pet_skill.c:1546-1630`）

输入 `data` 是 `|` 分隔的背包格号（`CHAR_CHECKITEMINDEX` 只要求 0 到 `CHAR_MAXITEMHAVE`−1，**穿在身上的格子也行**，`char_base.c:891`）。人物必须不在战斗中（`BATTLE_CHARMODE_NONE`），否则静默返回。

逐个读入的检查，**按格子在列表里的位置依次**（第一个不满足的就中止，已读的不回滚，因为这一阶段还没改任何东西）：

1. 格子不存在或空：**跳过**（不报错；位置照算，所以会造成后面的材料被忽略，见 1.6 第 1 条）。
2. 位置 ≥ 4：「精工每次只能选择四个物品。」
3. 和前面重复：只打服务端日志，不提示。
4. 精工类别码为空或 `NULL`：「这样物品不适合精工。」
5. 类别码含 `INSLAY`：第一个记为**武器/防具**；第二个：「精工每次只能选择一个武器或防具。」

读完后，没有武器/防具：「精工必须选择一个武器或防具。」

然后按**列表顺序**对每个材料做 `PETSKILL_ITEM_inslay`（见 1.4），**成功一个就立刻删掉这个材料**（`CHAR_DelItem`，整件物品，不分叠放）；某一个材料失败则整个函数返回，**前面已经镶上、已经删掉的不回滚**。全部成功后刷新武器防具那一格、重算数值并发 `P` 状态串（攻、防、敏、魅）。成功时**没有任何提示**。

### 1.4 `PETSKILL_ITEM_inslay`（`item/item_gen.c:1254-1366`）

对（武器防具，一个材料），顺序：

1. 材料不是武器防具本身；材料类别码非空且不是 `NULL`。
2. 解析武器防具的 `inlaycode` 为三格，没写的格子是 `NULL`；找第一个 `NULL` 格，把**材料的类别码**写进去。三格都有：「武器或防具已经镶满了。」，返回失败。
3. 把新的 `inlaycode` 写回武器防具。
4. **数值累加**：攻、防、敏（实际是 `ITEM_MODIFYQUICK`）、HP、MP、运气、伤、吸，八项各加材料的值，**没有上限**。（`worktyp` 数组最后一项是魔法 ID，求和循环 `i < arraysizeof(worktyp)-1` 不含它。）
5. **魔法覆盖**：材料的 `ITEM_MAGICID > 0` 时，武器防具的魔法 ID 和魔法 MP 被材料的值**替换**，不保留原来的；材料没有魔法则保持原样。
6. **函数覆盖**：`ITEM_FIRSTFUNCTION` 到 `ITEM_LASTFUNCTION` 之间的所有函数字段（init、preover、postover、watch、use、attach、detach、drop、pickup、die-relife）先全部清空，再用材料的同名字段填；**材料没有的，武器防具原来的也丢**。`ITEM_ARGUMENT` 同样被材料的参数替换。
7. **重写效果文字** `ITEM_EFFECTSTRING`：
   `攻±a 防±b 敏±c HP±d MP±e 伤±f 吸±g <魔法名>`，数字是累加后的**总值**（含装备本来的），非负时带 `+`，负数自带 `-`，运气不显示，魔法名取魔法表名称，没有魔法 ID 就是空。原来的效果说明（如“攻 +9 防 -3 敏 -3”）被整个替换。

### 1.5 数值怎么生效

穿在身上时，`item/item.c:1395-1430` 的 `itemEffect` 表把这些加成累加到人物上，并按表里各项给定的范围夹住（例如运气 1 到 5、MP 0 到 1000（单位 1/100）、伤吸 −100 到 100，攻防敏的上限是 `EQUIP_FIX_MAX`）。具体取值实现时照表抄，不在这里重复。魔法 ID 与 MP 决定该装备格的精灵（`docs/magic-acquire.md` 2.1、2.4）。

### 1.6 原版的毛病（新设计要避开的，不照搬）

1. **跳过空格造成材料被悄悄忽略**：列表里某位置的格子是空的，`itemindexs[i]` 保持 −1；后面“依次镶”的循环遇到第一个 −1 就 `break`，后面的材料既不镶也不删，也没提示。
2. **材料可以是身上穿着的东西**（0–4 格也合法），材料会把穿戴中的装备删掉。
3. **叠放**：删的是整件物品，不是 1 个。新服务端有叠放，合成（加工、料理）用的是“每格扣 1 个”（`docs/synthesis.md`）。
4. **失败不回滚**：第 2 个材料遇到“镶满了”，第 1 个已经镶上并删掉。这一条的行为**保留**（见 2.4），但新协议要在响应里说清楚镶了几个。
5. **函数和参数被材料清空**：武器防具原来的 attach/detach 等函数丢掉，是对装备的破坏，数据里没有任何物品用，保留原版行为，只是标注风险（见 2.6）。

## 二、设计

### 2.1 规则

| 规则 | 说明 |
|---|---|
| 谁能用 | 世界中的角色，不在战斗中（`IN_BATTLE`）、不在交易中（`IN_TRADE`，STAGE-294 做了之后）。原版不检查倒下，新服务端也不检查 |
| 对象 | **目标**：一件武器/防具（类别码含 `INSLAY`），可以在背包（5–19），也可以穿在身上（0–4）；**材料**：1 到 3 件，必须在背包（5–19）。比原版严的两处：材料不能是穿着的；格子是空的或重复，整条请求直接拒绝，不静默跳过 |
| 数量 | 目标算 1 件，目标加材料最多 4 件：材料超过 3 件回复原版台词「精工每次只能选择四个物品。」 |
| 镶嵌格 | 每件武器防具共 **3 格**，永久占用，没有卸下或洗掉的办法（原版没有） |
| 每个材料 | 占 1 格；累加 8 项数值；有魔法就覆盖魔法 ID 与 MP；覆盖使用函数与参数；重写效果文字 |
| 叠放 | 目标必须是单件（`count` = 1），不是则 `BAD_REQUEST`；材料叠放的格子**只用 1 个**（同加工、料理） |
| 顺序与中途失败 | 按请求里 `materials` 的顺序依次镶。第 k 个材料遇到“镶满了”就停止，前 k−1 个已经镶上并扣掉（**不回滚**，同原版），响应带 `applied` |
| 没有提示 | 成功时不发台词，客户端自己根据响应显示 |
| 数据启用条件 | 类别码来自物品模板（`itemset.txt` 第 4 列）和覆盖表（2.5）。模板和覆盖表都没写类别码的物品，视为空 |

### 2.2 校验顺序和台词

第一个不满足的就回复，**什么都不改**（中途“镶满了”是唯一的例外，见 2.1）：

| # | 检查 | 回复 | 台词（原版原文） |
|---|---|---|---|
| 1 | 控制权 | `CONTROLLED_BY_AGENT` / `CONTROLLED_BY_PLAYER` | 同其他操作类请求 |
| 2 | 战斗中 | `IN_BATTLE` | 原版是静默返回；新协议给错误 |
| 3 | 请求形状：`target` 是 0–19 的整数，`materials` 是 1 个以上整数、元素 5–19、不重复、不含 `target` | `BAD_REQUEST` | |
| 4 | 材料多于 3 件 | `INLAY_TOO_MANY` | 精工每次只能选择四个物品。 |
| 5 | 任一格为空 | `EMPTY_SLOT` | |
| 6 | 目标、材料依次检查类别码：空或 `NULL` | `INLAY_NOT_SUITABLE` | 这样物品不适合精工。 |
| 7 | 材料里出现含 `INSLAY` 的（第二个“武器防具”） | `INLAY_MULTI_TARGET` | 精工每次只能选择一个武器或防具。 |
| 8 | 目标的类别码不含 `INSLAY` | `INLAY_NO_TARGET` | 精工必须选择一个武器或防具。 |
| 9 | 目标不是单件 | `BAD_REQUEST` | |
| 10 | 依次镶，遇到目标已满 | `INLAY_FULL`（带 `applied`） | 武器或防具已经镶满了。 |

第 6、7、8 步的相对顺序按原版：先逐件检查（目标在前、材料依次在后），第一个撞到的先报；全部读完才查“有没有武器防具”。

### 2.3 协议草案

接在 `protocol.md` 最后一个 `5.x` 之后（编号以合并时为准）。操作类，世界中，玩家和 agent 都能发。

```jsonc
{"id": 60, "type": "item_inlay", "data": {"target": 5, "materials": [6, 7]}}
{"id": 60, "type": "item_inlay", "ok": true, "data": {
  "applied": 2, "consumed": [6, 7],
  "item": {"slot": 5, "item_id": 20, "name": "小斧头", "effect": "攻+11 防-3 敏-3 HP+0 MP+0 伤+0 吸+0 大地的精灵 Lv1", "count": 1,
           "inlay": {"role": "gear", "free": 1, "codes": ["RUBY", "RUBY", null]}}}}
{"id": 61, "type": "item_inlay", "ok": false, "error": {"code": "INLAY_FULL", "message": "武器或防具已经镶满了。", "data": {"applied": 1, "consumed": [6]}}}
```

- `target` 是目标格（0–19），`materials` 是材料格（5–19），都用 `inventory` 的格号。其他字段回复 `BAD_REQUEST`（拼错字段名不静默失效）。
- **响应**：`applied` 是实际镶上的件数，`consumed` 是被扣掉的材料格（每格 1 个，按请求顺序），`item` 是镶完之后的目标（格子不变）。中途失败时回 `ok: false`，`error.data` 带同样的 `applied` 与 `consumed`，物品已经变了，客户端以后续的 `inventory_changed` 为准。
- **推送**：成功或部分成功后，**先于响应**推 `inventory_changed`（5.18）；目标穿在身上时再推 `status_changed`（10.10，攻防敏、HP、MP 或精灵变了的完整 `status`）。
- **`inventory` / `inventory_changed` 的格子对象增加 `inlay`**，只对类别码非空的物品出现：
  - 可镶装备：`{"role": "gear", "free": 0–3, "codes": [码或 null ×3]}`；
  - 材料：`{"role": "material"}`。
  - 镶过东西的物品，`effect` 就是 1.4 第 7 条重写后的文字（客户端不用知道细节，直接显示）。
  当前数据下没有任何物品带 `inlay`，旧客户端忽略它即可。
- **错误码**（新增 5 个）：`INLAY_TOO_MANY`、`INLAY_NOT_SUITABLE`、`INLAY_MULTI_TARGET`、`INLAY_NO_TARGET`、`INLAY_FULL`。沿用：`BAD_REQUEST`、`EMPTY_SLOT`、`IN_BATTLE`、`CONTROLLED_BY_AGENT`、`CONTROLLED_BY_PLAYER`、`INTERNAL`、`IN_TRADE`（STAGE-294）。
- **agent 分级**（`agent-guide.md` 第 6 节）：**第三级，必须先问**。材料被消耗，镶嵌永久，会覆盖原有精灵，且无法撤销。

### 2.4 数据和存储

**模板**：`tools/gen-itemset.py` 增加三列：精工类别码（第 4 列）、初始镶嵌码（第 5 列）、伤（第 32 列）、吸（第 33 列）。HP、MP 的列号按 `item.c` 的 `ITEM_setintdata` 表和 gen-itemset 已有方法核对（HP/MP 现在也没有进模板，这是新服务端装备数值里本来就缺的两项）。新增列追加在 TSV 末尾，前面各列位置不变。

**覆盖表**（可选）：`server/gamedata/inlay_overlay.tsv`，格式 `物品编号\t类别码\t初始镶嵌码`，默认**只有表头、没有数据行**，用来在不改 `itemset.txt` 的前提下启用精工；加载时校验物品编号存在。测试用另一份固定数据（见 2.7）。

**物品行**：迁移给 `character_items` 加一列 `inlay jsonb NULL`，没镶过的物品是 `NULL`：

```jsonc
{"codes": ["RUBY", "RUBY", null],
 "bonus": {"attack": 2, "defence": 0, "agility": 0, "hp": 0, "mp": 0, "luck": 0, "other_damage": 0, "other_defc": 0},
 "magic": {"id": 20, "mp": 3},         // 只在材料带魔法时写，覆盖模板的魔法
 "use_func": "", "argument": "",        // 被材料覆盖后的值，只在发生覆盖时写
 "effect": "攻+11 防-3 敏-3 HP+0 MP+0 伤+0 吸+0 大地的精灵 Lv1"}
```

- `bonus` 存**材料累加量**，不存总值；最终值 = 模板 + `bonus`（比存总值好：模板改数据时不会出现两套数）。
- 物品行整体过户时（交易，`docs/trade.md`）`inlay` 随行走，不丢。
- 迁移编号以合并时为准，注意和 test 上别的需求撞号（见 `migration-number-collision-on-test`）。

**读取的地方**（给物品加上“实例覆盖”后要改的）：

- `equip_rules.go` 的 `equipBonus`：攻、防、敏、运气加上 `bonus`；新增 HP、MP、伤、吸的累计（这几项现在装备模板也没接入，见 2.6）。
- `equipmagic.go`：装备自带精灵先看实例的 `magic`，没有再看模板。
- 背包的 `inventory` 输出：`effect` 优先用实例的 `effect`，加上 `inlay`。
- 使用物品（`item_use`）读 `use_func` / `argument` 时也优先实例的。

### 2.5 流程（服务端）

1. 取角色锁；按 2.2 校验；读事务内的物品行。
2. 对每个材料依次：算出新的 `codes`、`bonus`、`magic`、`use_func`、`argument`、`effect`；满了就停。
3. **一个数据库事务**：把成功的材料扣掉（叠放的 `count − 1`，到 0 删行），写目标的 `inlay`；提交后改内存，推送。
4. 事务失败：回滚，回复 `INTERNAL`，内存不变。

### 2.6 和新服务端其他系统的关系

| 系统 | 关系 |
|---|---|
| 装备数值（`equip_rules.go`） | 现在只有攻防敏、运气、魅力（加暴击、抗魔），**没有装备的 HP、MP 加成，也没有伤、吸**。精工累加这些值，但它们要等装备数值接入后才在战斗里生效；在那之前效果文字照样显示，数值照样存。需要单独立项把它们接进来（HP、MP 对应原版 `CHAR_WORKMAXHP/MAXMP`，伤吸对应 `battle_event.c:1119`） |
| 精灵（`equipmagic.go`、`magic_use`） | 目标穿在身上时，镶完立刻影响该装备格的精灵；不在身上则穿上时才生效 |
| 耐久（`durability.md`） | 不变；耐久、受损等级、合成标记都留在原行 |
| 交易（`trade.md`） | 交易中不能精工；交易物品行时 `inlay` 随行走；卖给商店按模板价 |
| 合成 `merged` 标记 | 不受影响 |
| 函数覆盖 | 新服务端只建模了使用函数与参数；装备函数（attach、detach 等）没有，所以实现里只处理这两项。数据里没有物品会触发，风险记在这里 |

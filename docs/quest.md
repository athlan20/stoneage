# 任务 NPC（STAGE-90）

原版的任务 NPC（`enemy=changeevent`，脚本是 `data/npc` 下的事件文件）在新服务端上的实现。按下面的分批清单逐批放开：
第一批「成人仪式」接任务、领仪玉、交仪玉、完成后闲谈全部可玩；最新一批（STAGE-220）放开「精灵王的传说」（`king` 目录
13 个脚本，任务 49–54）。其余任务 NPC 的数据已经全量转换，但没有放开，对话回复 `NPC_NOT_TALKABLE`。对照源码：
`original-data/gmsv/npc/npc_exchangeman.c`（解析和执行）、`npcutil.c`（事件位）、
`data/npc/jaruga/event/`（成人仪式的脚本）、`data/npc/king/`（精灵王的传说）。

## 数据

- `tools/gen-npcs.py` 扫描 NPC 创建文件，`enemy=changeevent` 的 NPC 进入 `server/gamedata/npcs.tsv`（显示类型「任务」，
  协议 5.32），脚本内容由 `tools/npcevent.py` 解析成 `server/gamedata/npc-event.json`（每个 NPC 一行，编号与 NPC 表一致）。
  台词参数的格式转换在 `tools/npc_records.py`。重新生成：`python3 tools/gen-npcs.py`。
- 当前结果：303 个任务 NPC，1411 个事件块，其中 **1366 块支持、45 块不支持**（不支持的块运行时不放行，见下文）。
  （STAGE-93 之前是 1064 / 347；NpcWarp 补齐后 1106 / 305；暗号补齐后 1160 / 251；STAGE-94 补断行台词、`AcceptMsg\n`
  写法和放弃撤销、STAGE-97 补分页台词之后 1265 / 146；STAGE-197 补宠物之后 1360 / 51；STAGE-219 读懂 `NOW=n` 和 DelItem
  末尾逗号之后 1366 / 45。）
- 每个块的记录（`server/gamedata/npcevent.go` 的结构）：`type`（MESSAGE / ACCEPT / REQUEST / CLEAN）、`event`（原版 EventNo，
  -1 表示没有进行中事件）、`cond`（EVENT：外层逗号是或，内层 & 是与）、`msg`（台词，逐字保留，字面的 `\n` 已转成换行）、
  `get_item` / `del_item` / `get_rand` / `get_stone` / `del_stone` / `charm` / `end_set` / `clean` 动作，以及
  `unsupported`（不支持的原因，空表示支持）和 `keyword`（暗号原文，逐字；空表示不是暗号块，见下文「暗号」）。

## 选块与对话（原版 NPC_TypeCheck、NPC_MsgDisp）

1. 块按文件顺序看，**第一个命中的块**生效。跳过的情况：事件已完成（EventNo 对应的完成位已置位）、暗号块（说的话和暗号不同，
   见下文「暗号」）、条件不满足。
2. 遇到不支持的块（而且它没有被前面的完成/暗号跳过）时，**拒绝对话**（`NPC_NOT_TALKABLE`），不让后面的块替它说话。
3. 没有块命中时，随机说一句 `NomalMainMsg`（逗号分句）。
4. 四类块：
   - **MESSAGE**：先做物品交易（失败只说对应台词），再设进行中（EventNo 不是 -1 时）、EndSetFlg、CleanFlg，然后说 `NomalMsg`
     （没有时说 `NomalWindowMsg`）。没有台词的块什么都不做。
   - **ACCEPT**：问 `AcceptMsg`（是/否；台词可能分页，见下文「分页台词」）。选是：交易（DelItem、DelStone、GetRandItem、GetItem、GetStone，失败说 `ItemFullMsg` /
     `StoneLessMsg` / `StoneFullMsg`），成功后 EndSetFlg、Charm（事件号大于 0、魅力不满 100，封顶 100）、CleanFlg，最后说 `ThanksMsg`。
   - **REQUEST**：未进行中时问 `RequestMsg`（是/否）；选是：交易，成功后设进行中，EndSetFlg、CleanFlg，说 `ThanksMsg`；选否什么都不做。
     进行中时问 `StopMsg`（是/否）：选是，清进行中、魅力减 1（大于 0 时），说 `EndStopMsg`；选否说 `NoStopMsg`。
   - **CLEAN**：问 `CleanMainMsg`（是/否）；选是：CleanFlg 列出的事件清完成和进行中（可以重做），说 `CleanFlgMsg`。
5. 问答窗口的选项：1 是、2 否（`npc_window.options`，协议 5.34 / 5.35）；分页台词的窗口还有 `下一页` / `上一页`（见下文「分页台词」）。
   每一步都按条件重新选块，块已经不是开窗时的那一块就只关窗。

## 条件和动作

| 条件 | 含义 | 状态 |
| --- | --- | --- |
| `ITEM=编号` / `ITEM=编号*数量` / `ITEM!=编号` | 背包（不含穿戴）里有 / 数量够 / 没有；数量按堆叠数累计 | 支持 |
| `LV=` `LV<` `LV>` | 角色等级 | 支持 |
| `ENDEV=n` / `ENDEV!=n` | 事件 n 已完成 / 未完成 | 支持 |
| `NOWEV=n` | 事件 n 进行中 | 支持 |
| `NOW=n` | 原版不认 `NOW` 这个标记（NPC_EventFreeIfCheck 没有分派），恒不成立，所以含它的候选组整组丢掉；其余组照常。全部组都丢掉的块省略（原版永远选不中）。转换时列出丢掉的组和省略的块（`tools/npcevent_now.py`，STAGE-219） | 支持（STAGE-219，只认 `NOW=整数`） |
| `TIME!=n` | 游戏时段（0 夜、1 晨、2 午、3 晚）不是 n | 支持 |
| `NOWEV!=n` | 原版恒为真（疑似原版错误，只在 `extra/event/marju01`） | 不支持 |
| `PET<比较符><等级>-<编号>[*数量]` | 宠物等级比较，数随身的宠物（不数寄放和任务送的），见「宠物」 | 支持（STAGE-197）；带 EV 的变种（只数任务宠物）不支持 |
| `SP=`、`DR…` | 存档点、庄园（DR 在原版里没有分派，恒不成立） | 不支持 |

| 动作 | 含义 | 状态 |
| --- | --- | --- |
| `GetItem` / `DelItem` | 给 / 收道具，`编号*数量` 每件占一格；`DelItem:编号` 不写数量时收走背包里所有这个编号。`DelItem` 末尾可以多一个逗号（STAGE-219，原版把空项当编号 0，什么也不做）；`GetItem` 的末尾空项和中间的空项仍不支持 | 支持 |
| `GetStone` / `DelStone` | 给 / 收石币；`DelStone` 写 `LV*N` 时按等级算 | 支持 |
| `GetRandItem` | 从列表里随机给一件 | 支持 |
| `EndSetFlg` / `CleanFlg` | 设完成（清进行中）/ 清完成和进行中 | 支持 |
| `Charm` | 魅力（ACCEPT 块，见上） | 支持 |
| `NpcWarp` | 把 NPC 自己移到脚本给的位置（轮流用，全服生效，见下文「NPC 移位」） | 支持（STAGE-93） |
| `KeyWord` | 玩家说暗号才触发 | 支持（STAGE-92，见「暗号」）；只有同时带其他不支持字段的块（1 块，带 `PetFullMsg`）仍不支持 |
| `DelPet` / `GetPet` / `PetFullMsg` | 收、送宠物（见「宠物」）；只在 MESSAGE、ACCEPT 块里 | 支持（STAGE-197） |
| `GetEgg` / `Pet_Name` / `pet_skill` | 宠物蛋、改名、宠物技能 | **不支持** |
| `AcceptMsg1..7`、`ThanksMsg1..4`、`RequestMsg1..3`、`NomalWindowMsg1` 等 | 分页台词（Next/Prev） | 支持（STAGE-97，见「分页台词」）；只认这四类台词，`NomalMsg1` 等仍不支持 |
| `DelItem:EVDEL` / `NotDel` | 按命中的条件删道具，NotDel 里的编号留下（见「宠物」） | 支持（STAGE-197） |
| `Break` | 道具坏了 | **不支持** |
| REQUEST 带 `GetItem` / `DelItem` / `DelStone` | 接任务时交易，放弃时撤销（见下文「放弃时撤销」） | 支持（STAGE-94） |
| REQUEST 带 `GetRandItem` / `GetStone` | 放弃时的撤销没有对应的原版行为 | **不支持** |
| REQUEST 带 `DelPet` / `GetPet` | 放弃时的撤销没有对应的原版行为（收走的宠物找不回来） | **不支持**（STAGE-197） |

不支持的块：没有被完成或暗号跳过时，对话被拒绝（选块第 2 条）。KeyWord 块只在玩家说暗号时才考虑，普通对话直接跳过，不拒绝。

## 暗号（STAGE-92）

原版 `npc_exchangeman.c` 的 `NPC_TypeCheck`：块有 `KeyWord` 时，玩家说的话必须和它 `strcmp` 相同才往下看条件；
普通块不看说的话，照常按条件选。这里照搬：

- **匹配规则**：逐字完全相同，区分大小写和全半角，不去空格（客户端 `reply` 原样发送，服务端只去掉首尾的换行）。
  空的说话内容不匹配任何暗号块。
- **匹配了暗号但条件不满足**：接着看后面的块，和原版一样。
- **没有块命中**（包括说错了）：说一句闲聊（`NomalMainMsg`），不扣东西、不改进度。
- **“说暗号”选项**：脚本里还有没完成的暗号块时，NPC 的文字窗口（闲聊句，或者 MESSAGE 块的台词）上多一个 `1. 说暗号`。
  选了以后窗口转成文字输入（`accepts_text`），玩家用 `reply 暗号` 说出来（协议 5.34、5.35、5.37）。问答窗口（是/否）上没有这个选项。
  暗号块没有事件号，永远不算完成，所以说过一次之后选项还在（再说一次只会是闲聊）。
- **命中的块**和普通块一样执行：MESSAGE 直接做，ACCEPT / REQUEST / CLEAN 再问是/否。问答窗口记下说的暗号，之后的选择也按它选块。
- 数据：`tools/npcevent.py` 把 `KeyWord:` 的原文保存进 `keyword`。转换后 55 个暗号块，54 个支持（只有带 `PetFullMsg` 的 1 块仍不支持）。

与原版的差异：
1. 原版暗号是玩家在聊天框里说的任意一句话（`szMes`），这里用“说暗号”选项和文字输入窗口代替（聊天还没有做，见需求 STAGE-92
   的交互方案）。
2. 原版没有“说错了”的台词，这里说的是闲聊句（`NomalMainMsg`），需求里就是这样写的。
带物品的 REQUEST 要写清楚放弃时的收回才能放开，所以整块标不支持。

传送员的通行条件（FREE，`server/gamedata/warpcond.go`）也能用任务进度：`ENDEV=n`（`!=` 同样支持）、`NOWEV=n`（只有 `=`）
按上面的同一套进度判断，`ITEM!=` 是背包里没有这个道具。庄园（`MANOR`）、家族（`FM`）的条件仍然不支持，4 名传送员因此跳过
（`NPC_NOT_TALKABLE`）。这是 STAGE-88 带任务条件的传送员的基础。

## 分页台词（STAGE-97）

原版 `npc_exchangeman.c` 用 `WINDOW_BUTTONTYPE_NEXT / PREV` 翻页：台词写成 `AcceptMsg1..N`（或 `AcceptMsg` 加 `AcceptMsg2..N`），
`RequestMsg`、`ThanksMsg`、`NomalWindowMsg` 同理。转换时按页序收进 `msg.paged`（键是 accept、thanks、request、nomal_window，
值是全部页），有分页的台词不写单页字段；页号必须连续，否则块标不支持。`EventMsg.Pages(kind)` 统一取页（单页台词也当一页）。

窗口上的翻页（协议 5.35）：

- **问话（ACCEPT、REQUEST）**：非最后一页的选项是 `1 下一页`，第 2 页起多 `2 上一页`；最后一页才是 `1 是、2 否`（第 2 页起再加
  `3 上一页`）。交易和进度只在选“是”之后结算，翻页不改任何数据。
- **读完的台词（感谢话、MESSAGE 台词）**：交易在选“是”之后已经做完（感谢话是交易之后的话，见「与原版的差异」3），翻页只换显示的页；
  没有“是/否”。非最后一页是 `1 下一页`（第 2 页起加 `2 上一页`）；最后一页的选项是 `上一页`（第 2 页起），脚本还有没完成的
  暗号块时最后一页上多 `说暗号`（STAGE-92，放在最前）。
- 每次翻页先推 `npc_window_closed`（`CHOSEN`），再推新的 `npc_window`，和问答一样。
- **选块**：问话的每次翻页都先按条件重新选块，块已经不是开窗时那一块就只关窗（和选“是/否”一样）。读完的台词不再选块：
  它的事件已经完成，重选会跳过它，窗口就直接关掉。
- 页号只记在窗口上，关窗（`npc_close`）后再对话从第 1 页开始。翻页、关窗都不改背包、金币、任务进度。

**白名单**：分页（STAGE-97）本身不改白名单。含分页台词和宠物块的 `king/event69_1` 已在 STAGE-220 随 `king` 目录一起放开；
分页能力当时用 `Options.NpcEventEnabled` 临时放开 `king/event69_1` 和 `jaruga/event/event01_2`（草药，感谢话 4 页）验证。

## 事件位与任务进度

- 原版用事件号的位图记完成（ENDEV）和进行中（NOWEV）。这里分两处存，不另存位图：
  - 事件号映射到任务表（`server/gamedata/quests.tsv`，STAGE-86）里的任务编号（任务表里完成事件号和进行中事件号总是相同），
    进度写在 `character_quests`（每个任务一个状态：进行中或已完成）。
  - **不对应任务表的事件号**（脚本里只有事件号的中间步骤，如造斧的 19 号、20501 链路）按事件号写在 `character_event_flags`
    （迁移 0015，STAGE-94）。规则和任务一样：一个事件号只有一种状态，清除删掉这一行。进入世界时和任务进度一起读一次。
- 脚本只看事件号，两处的差别由 `server/character/npcevent_flags.go` 的 `progress` 屏蔽：任务和事件共用同一套状态规则。
- 一个事件号可能对应几个任务（5 组：225、136、65、140、145），原版也是一起完成的，这里同样一起改。
- 一个任务只有一种状态：已完成的任务不会被设回进行中；清除（CleanFlg、放弃）删掉这一行。
- 交易的背包、金币、任务进度在**一个数据库事务**里写入，写成功后才改内存、推送 `inventory_changed` / `status_changed` /
  `quests_changed`（消息栏的“任务【…】进行中”由客户端根据 `quests_changed` 显示）。任何检查失败，什么都不写。
- 魅力只在内存里改，离开世界时随角色保存（同原版的角色数据）。
- 魅力的几条增减途径：战斗增减（`fortune.go`）和美容师（`charm.go`，见 `docs/protocol.md` 5.64）经 `gamedata.ClampCharm` 夹在 0–100；任务脚本的 `Charm` 动作（`npcevent_steps.go`）只做封顶 100（加的是正数，不会低于 0）。

## NPC 移位（STAGE-93）

对照 `npc_exchangeman.c` 的 `NPC_EventWarpNpc`。`NpcWarp` 写成 `地图.x.y,地图.x.y,…`（地图必须真实存在，转换时检查），在脚本的一步
**交易成功之后**执行：MESSAGE 说话、接任务、交付（放弃和重置没有 `NpcWarp`）。

- **轮转**：每个 NPC 记一个下标（原版 `CHAR_WORK_EVENTWARP`，初始指向第一个）。每次移动用下标指的位置，下标往后挪，用到最后一个
  之后回到第一个。下标属于 NPC，不属于块：同一个 NPC 的不同块共用一个下标。
- **全服共用**：`server/gamedata/npcboard.go` 的 `NPCBoard` 记录移动后的位置，`npcs.tsv` 是初始位置。列表（5.32）、对话（5.33）、
  `npc_find`（5.43）都读它。只在内存里：服务重启后回到初始位置，轮转进度也归零（原版同样不落库）。
- **不在角色锁里改**：交易成功时只登记（`Live.warps`，`server/character/npcwarp.go`），`talk` / `npc_choose` / `npc_reply` 处理完、角色锁放开之后
  才移动并推送。`NPCBoard` 是叶子锁，不调用别的锁。
- **推送**：原地图和新地图上的连接收到 `npcs_changed`（协议 5.46）。原地图上别的连接正开着这个 NPC 的窗口时，先以 `MOVED` 关掉它
  （协议 5.34）；触发移动的连接自己的窗口不关，台词照常看完。
- **放开**：只有脚本的块全部支持才放开（见下文「白名单与分批」）。第二批（STAGE-93）：`jaruga/event/ruri03`（伊布）、
  `giiru/event/sink/sink01`、`giiru/event/sink/sink055`、`giiru/event/sink/sink055a`、`poru/mary02`、`poru/samugiru`。

与原版的差异（NPC 移位）：

1. 交易不成立（背包空位、金币不够）时不移动，和原版 `NPC_AcceptDel` 失败直接返回一致。
2. 坐标不查地图边界：原版 `CHAR_warpToSpecificPoint` 的边界处理这里没有对照，数据里的坐标原样保存（如 `200.215.1017`；地图 200 的
   NPC 本身就有 y 到 1005 的）。

## 放弃时撤销（STAGE-94）

放弃（REQUEST 的 `StopMsg` 选是）时，把接任务的交易反过来做（`server/character/npcevent_refund.go`）：

- **收回**接任务时给的道具（`GetItem`，按脚本写的件数收回；背包里没有就算了）。
- **退回**接任务时收走的东西：`DelItem` 实际删掉的件数（`DelItem:编号` 不写数量时按实际删掉的件数记）和 `DelStone` 扣的石币。
- **记录**：接任务成功时，把实际收走的道具和石币写进 `character_event_refunds`（迁移 0014，按事件号一行，和交易同一个事务）；
  放弃成功后删掉这一行。没有收走东西的接任务不写。只有带事件号的 REQUEST 能放弃（事件号 -1 的块没有进行中状态），所以只记这种块。
- **背包放不下**：收回在前、退回在后（收回的格子可以给退回用）。退回的道具放不下时说 `ItemFullMsg`，放弃不成立：任务还在，
  记录还在，背包不变（对照原版 `NPC_ItemFullCheck` 失败后 `NPC_MsgDisp(4)` 直接返回）。石币超过上限时说 `StoneFullMsg`，同样不放弃。
- **石币**：石币只在内存里改，离开世界时随角色保存（同魅力，见「事件位与任务进度」）。
- **现有脚本里的退款路径很窄**：启用的脚本里只有沙拉（`event20_6`，事件 21）的接任务块收走道具（`DelItem` 2487）。它的放弃块
  条件也要求背包里有 2487，而接任务时已经收走了，所以正常流程里放弃走不到（再说话只是闲谈，见协议用例 `npc_quest_giveup_refund`
  的第二步）；只有再拿到一件 2487 之后才能放弃，退款在那时才起作用。这是原版数据的样子，不是这里的实现问题。

需求里写的是“按原版 `NPC_EventAdd(mode 1)` 退回”。原版 mode 1 实际上只做两件事：`GetItem` 收回（`NPC_EventDelItem`），
以及把 `DelItem` / `DelStone` 再执行一遍；没有任何退回。这里按需求的意思实现：退回接任务时收走的东西，并保留原版的收回。

## 宠物（STAGE-197）

对照 `npc_exchangeman.c` 的 `NPC_PetLvCheck`（条件）、`NPC_AcceptDel`（ACCEPT 和 MESSAGE 的交易，收、送宠物）、`NPC_EventAdd`
（接任务时送宠物）、`NPC_EventDelPet`、`NPC_EventAddPet` 和 `NPC_EventDelItemEVDEL`。转换在 `tools/npcevent_pet.py`，运行在
`server/character/npcevent_pet*.go`。

- **条件 `PET<比较符><等级>-<编号>[*数量]`**：`=`、`<`、`>` 比的是宠物等级（`PET<30-720` 是等级小于 30 的 720 号），编号是宠物
  模板编号。数量缺省为 1，条件要求随身栏位（5 个）里符合的宠物至少有这么多只。骑乘和出战的照样算，寄放在宠物店的不算，任务送的
  （`event_given`）不算。和 `ITEM`、`LV` 一样放在 `EVENT:` 里，`&` 是与，`,` 是或。带 `EV` 的变种（只数任务宠物）不支持。
- **`DelPet:<宠物项>[,<宠物项>…]`**（直接写）：先逐项检查，每项各自数（同原版）。有一项不够，整个动作不做，**不说话**：原版
  `NPC_AcceptDel` 直接返回，没有台词。战斗中收不了，同样不做、不说话。都够了再逐项收：写了 `*n` 的收 n 只，按栏位从小到大；没写
  数量的收走所有符合的（至少要有 1 只）。每只收走的宠物提示“交出XX。”。骑乘中的宠物也收走（删掉它的行，骑乘状态也就没了）。
- **`DelPet:EVDEL`**：取 `EVENT:` 里命中的那一组（逗号分的第几项），收那一组里的 `PET` 项，检查和收法同上。
- **`DelItem:EVDEL` 与 `NotDel:编号[,编号…]`**：取命中的那一组里的 `ITEM=编号[*数量]` 项收道具，`NotDel` 里的编号留下。没写数量
  的收走背包里所有这个编号的道具（原版 `NPC_EventDelItemEVDEL`）。`ITEM!=` 项原版也会删（它取的是 `=` 后面的编号），写法不明，
  这里标不支持。`NotDel` 只能和 `DelItem:EVDEL` 一起用。
- **`GetPet:编号[,编号…]`**：编号是怪物编号（`enemy.txt` 的 ENEMY_ID），不是宠物模板编号；多个时随机选一个。块里必须有
  `PetFullMsg`（转换时检查）。加载时检查：怪物要在敌人表里，它的宠物模板要在宠物表里，查不到的块标不支持。送出的宠物按怪物
  生成：等级在怪物的等级范围里随机（`RAND`，两端都算），资质和能力用 `NewPetGrowth`（同捕捉和 givepet），血量满，技能取模板，
  品质按模板，状态休息，放进第一个空的随身栏位。提示“拿到XX。”。
- **宠物栏满**：收完之后随身栏位没有空的，说 `PetFullMsg`，整笔交易不做（道具也不给）。收宠物在前，所以收走的那一只的栏位可以给送来的宠物用。
- **任务送的标记（`event_given`，迁移 0019）**：只有接任务（REQUEST 的“是”）送出的宠物打标记，同原版 `NPC_EventAdd` 的 mode 0
  设 `CHAR_ENDEVENT`。ACCEPT 和 MESSAGE 经 `NPC_AcceptDel`，原版不设（见「与原版的差异」）。标记不对玩家显示。
- **REQUEST 不支持宠物动作**：接任务时的 `DelPet` / `GetPet` 放弃时没有对应的原版撤销，整块标不支持（转换时判断）。
- **写库和推送**：交易成功后，在和道具、金币、任务进度同一个事务里写 `character_pets`（删掉收走的行，插入送出的行），然后推送
  `pets_changed`（5.20）和每只宠物一条 `notice`。只说台词、没有交易的块不动宠物。

## 宠物对话（STAGE-234）

原版 `data/npc/pettalk/*.arg`（宠物对话，`gmsv/char/pet_event.c` 的 `PET_Talkfunc`）。转换在 `tools/pettalk.py`，生成
`server/gamedata/pettalk.json`；选块在 `server/gamedata/pettalk.go`，执行和个体上限在 `server/character/pettalk.go`。

- **选块**：宠物等级 ≥ 它的有效上限时只看 `EVENTRUN` 块，否则只看 `TALKRUN`，`BOTH` 两种都看。条件：`FREE:LV>0`（恒成立）、

  `OTHER` 的一句（逗号分句，随机一句）。

## 与原版的差异

1. **清进行中用 AND NOT，不用 XOR**：原版 `NPC_NowEventSetFlgCls` 用异或，对没有置位的事件号会把它置上（原版错误）。需求写的是
   “清掉进行中位”，这里照需求做。
2. **选否不说话**：原版 REQUEST 的 `RequestMsg` 窗口选否时没有任何台词（`REQMAINMSG` 的 NO 分支为空）。验收口径第 1 条写的是
   “选否说原版拒绝话术”，与原版不符，**本期按原版实现**，等确认后再决定是否补台词。
3. **感谢话在交易之后**：原版 ACCEPT 先说 `ThanksMsg`，点 OK 后才交易；这里交易成功后再说感谢话。交易不成立时只说失败台词
   （原版会先说感谢话、再说失败台词）。
4. **费用占位**：台词里的 `%8d`（原版 sprintf 的金币数，前面补空格）直接换成数字。
5. **台词里的换行**：字面的 `\n` 转成真换行（客户端按行显示）。原文里台词断成两行的（23 块，如“就会付打工工资给你哦。”）
   STAGE-94 起把第二行直接接在第一行后面（不加换行，原文的断行处本来就是句中或字面 `\n` 之后）；原版只认第一行，续行会丢。
   字段名后面直接是字面 `\n`、没有冒号的写法（`AcceptMsg\n你…`，4 块）同样视为 `AcceptMsg:\n你…`。
6. **NOWEV!=** 不照搬原版的恒真（见条件表）。
7. **物品名**：2418 在物品表里叫「仪之兜」（头部装备：防 +15、敏 -3），需求里写作“成人证”，以物品表为准。
8. **事件位的存法**：原版是按事件号的位图（ENDEV / NOWEV）。这里任务表里的事件号按任务存（`character_quests`），其余事件号按
   事件存（`character_event_flags`，STAGE-94 问题 1 之前这些事件号什么都不记，造斧链路因此卡住）。两者的状态规则相同；但任务页只列
   任务表里的任务，中间步骤（如 19 号）不在任务页上出现。
9. **放弃撤销**：原版 mode 1 再执行的 `DelItem` / `DelStone` 不照搬（见「放弃时撤销」）。
10. **收不成时没有台词**（STAGE-197）：任务书写的是“失败说该块的失败台词”，但原版 `NPC_AcceptDel` 的 DelPet 检查直接返回
    FALSE，没有台词，这里按源码：不说话。宠物栏满的 `PetFullMsg` 是原版的台词（`NPC_MsgDisp` 10），照常说。
11. **送宠物的任务标记只在接任务路径**（STAGE-197）：任务书写的是送出的宠物都要打标记。原版只有接任务（`NPC_EventAdd` mode 0）
    才打：ACCEPT 和 MESSAGE 的送宠物走 `NPC_AcceptDel`，调用的是 `NPC_EventAddPet(…, 1)`，不打。这里照原版实现。
    结果是：当前能送出宠物的块都是 ACCEPT 或 MESSAGE，所以目前没有带标记的宠物；标记的代码只给 REQUEST 用，而 REQUEST 的宠物动作没放开。
12. **随机选编号**（STAGE-197）：原版用全局 `rand()`，这里用脚本的随机源（测试里固定）。
13. **没有默认宠物**（STAGE-197）：原版收走默认出战宠物时会清 `CHAR_DEFAULTPET`，本服务端没有这个概念，不处理。
14. **萨姆吉尔的勾玉单开**（STAGE-333）：原版勾玉链绑在红暴（事件 63）上，改写和新增的块、为什么改，见下文「萨姆吉尔的勾玉」。原版 GBK 脚本不动，改写在转换时叠上（`tools/npc_event_overlay.py`）。

## 块的结束（STAGE-223）

**原版怎么切块**（`original-data/gmsv`，只读）：

- 读文件：`npc/npcutil.c:1014-1017` 按行读，去掉换行后用 `|` 连起来（`NPC_Util_MargeStrFromArgFile`）。
- 切段：`npc/npc_exchangeman.c:93`、`:248`、`:1197` 用 `getStringFromIndexWithDelim(argstr, "EventEnd", i, …)`；
  `util.c:949-982` 找的是 `EventEnd` **子串**，不是整行。找不到时，剩下的文字整段作为最后一段返回 TRUE（`util.c:971-979`）。
- 认块：`npc/npc_exchangeman.c:255-256` 取不到 `EventNo` 的段直接 `continue`，不算块。

**结论**：

1. **文件末尾的块没有 `EventEnd`**：原版不丢，读到文件结束，照常当一块。转换器（`tools/npcevent.py` 的 `parse_script`）
   原来把它标成“缺少 EventEnd”，现在同样当块结束。
2. **`EventEnd` 后面同一行接了别的字**：这段文字属于下一段；下一段没有 `EventNo` 就跳过（原版 `continue`）。
   `poru/titan` 的块 7（0 起，REQUEST，事件 65）就是这种情况：`EventEnd` 后面粘着一句“这里是玛丽娜丝姊姊的海底宫殿哦！……”。
   原版照常读出这个块。之前转换器按整行匹配 `EventEnd`，把这句话和块拼在一起，报“缺少 EventEnd”，整本脚本放不开。
   **原版没有坏，是我们的转换器解析不一致**。修复后 `poru/titan` 的 8 个块全部支持，但**没有加进白名单**（放不放由后续需求决定）。
3. **没有 `EventNo` 的段**：原版跳过。`giiru/event/garunaev6` 有一处 `EvebtNo:-1`（拼写错误），原版取不到 `EventNo`，跳过。
   转换器照做，这一段不计为不支持块，转换说明里记一条（`段 N 没有 EventNo，原版跳过`）。
4. **注释里的 `#EventEnd`**（`extra/event/M_3000`、`poru/boy01`）：转换器把整段 `#` 开头的注释当成不存在；
   **原版不是这样**。`npc/npcutil.c:1087` 的 `strstr` 不认 `#`，注释段里的 `#EventNo:-1` 会被当成 `EventNo`，
   `#TYPE:ACCEPT` 也会被认成 `TYPE`。所以这两个文件里被注释掉的块，原版可能会真的执行。转换器暂时仍丢弃，
   这是**和原版不一致的已知点，待确认**（需要实际进游戏对照）。

**全量扫描**（`data/npc` 下 313 个含 `EventNo` 的文件，扫描脚本不入库）：

## 采伐许可证与涛、岚两线（STAGE-345）

**问题**：采伐许可证 2478 一个角色只能拿一张（赛尚 `jaruga/event/20501ev5` 块 16 用推荐书 2467 换，2467 只有巴尔 `ev3` 给一次），却被两处收走：涛线（`poru/team02` ACCEPT 56，交许可证和 30 级迪欧换涛之圣石 18557）和岚线（`20501ev5` 块 1，14 个良木 2468 换杉的手环 2481，同时 `DelItem` 收走 2468、2478、2467）。玩家做完岚线的手环，就没有许可证交给涛线，四颗圣石集不齐。

**改法**（覆盖层，`tools/npc_event_overlay.py` 的 `LICENSE_PATCHES`，原版 GBK 脚本不动）：只改 `20501ev5` 块 1（ACCEPT，事件 -1）。
- `del_item` 去掉 2478，保留 2468（全部）和 2467（全部，原样）。
- 条件加两项：`ITEM!=2481`（身上已有手环不再给）和 `ENDEV!=187`（发过手环后不再给）。
- 发过手环后设一次性事件 187（`end_set`）。187 不在任务表里，只作开关，见 `server/gamedata/npc-event.json` 块 1 的 `end_set`。

**刷奖检查**：只去掉收 2478，没有别的条件时，许可证不被消耗，玩家攒够 14 个良木就能反复换手环和 20000 石币。手环能不能丢弃、卖出或入库，原版数据里没有核实，所以只靠 `ITEM!=2481` 不够；一次性事件 187 把它堵死。许可证的总量没有变：2478 仍只能由块 16 用 2467 换，块 2~14 的石币块仍收 2478。这次唯一的变化是手环块不再消耗许可证，每个角色多一次用处，而且只有一次。

**残留（原版也是这样的选块规则）**：脚本按顺序取第一个成立的块。持有许可证的角色在赛尚处只要良木数匹配任一块（块 1 因上面的条件不再成立时），许可证就会被换成石币。测试中（纯逻辑）：发过手环后再带 14 个良木，选中块 2（13 个良木的块：收许可证、给 16000 石币）。所以涛线要先交，再去赛尚处换良木。

**对原版的偏离（有意）**：原版块 1 每次都收 2478。原版真实机制无从核实：`NPC_EventSetFlg`、`NPC_EventSetFlgCls` 等函数体不在源码树里，原版服务端也不在运行，无法确认原版是否有别的途径让两线同时完成。攻略要求四颗圣石都能拿到，所以在覆盖层里偏离。以后查到原版的真实机制，可以删掉 `LICENSE_PATCHES` 回到原版，并把本节改成原版结论。

**测试**：`server/character/npcevent_stage345_test.go`，纯逻辑，用真实白名单、真实选块和真实交易。整链：同一角色有 2478 和 14 个良木 → 赛尚给手环，2478 仍在包里，一次性事件 187 设上 → 再把 2478 交给米兰达队长（`poru/team02` ACCEPT 56，事件 56 进行中，30 级迪欧）换涛之圣石 18557，两步都成功。反向：13 个和 1 个良木的块（2、14）仍收 2478、不给手环；没有许可证时 14 个良木不给手环也不收良木；已有手环、或发过一次性事件（手环丢了）时，手环块不再命中。

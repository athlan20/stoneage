# 玩家交易（设计）

状态：**设计已定稿**（STAGE-293，2026-10-25，“待拍板”第 1–4 条已确认），尚未实现。规则对照原版服务端 `original-data/gmsv/char/trade.c`（959 行，协议 `lssproto_TD`），协议和界面按新服务端现有的真人组队（`protocol.md` 5.67）、社交开关（5.69）的写法重新设计。落地时按末尾的拆单顺序做，规则并入 `protocol.md`、`ui.md`、`interaction.md`、`agent-guide.md` 第 6 节，本文随后只保留设计依据。

**说人话**：两个玩家面对面，各自把想给的东西（最多 2 件物品、一些石币、1 只宠物）放到桌上，双方都看清楚、都点“锁定”、再都点“确定”，东西才一起换过去。中间任何一方改了报价，双方的锁定都作废，重新看；任何一方反悔或掉线，整个交易取消，什么都不会少。

## 一、原版怎么做（原版服务端 `trade.c`）

| 方面 | 原版行为 | 出处 |
|---|---|---|
| 怎么发起 | 面朝对方站在正前方一格，点“交易”（`TD|D`）。前方没人、不止一人、对方不是玩家，各有一句提示。**没有“对方同意”这一步**：对方只要交易开关开着，窗口直接在双方打开 | `TRADE_Search` |
| 谁不能被交易 | 对方在战斗中、组队中、交易开关（`CHAR_ISTRADE`）关着、已经在交易中。自己也不能在组队、战斗、交易中 | `TRADE_Search` |
| 报价内容 | 每方 **2 个“物品或石币”位 + 1 个宠物位**。物品必须在背包格（不含已穿戴的装备格），石币不能超过自己手上的钱，宠物必须存在 | `TRADE_HandleItem/Gold/Pet`，`CheckItembuf` 的 `a b c` 三位 |
| 对方能看到什么 | 物品：图、名字、效果文字、耐久损坏百分比；石币：数字；宠物：图、名字、等级、攻、防、敏、血上限、转生次数 | `TRADE_Handle*` 的 `outmess` |
| 确认步骤 | 两步。`TD|C` 锁定自己（之后改报价会直接关闭交易）；双方都锁定后再发 `TD|K` 确定；两边都发过 `K`，且双方最后的报价互相吻合，才真正交换 | `TRADE_ShowItem` 的 `c`/`k` 分支、`TRADE_SwapItem` |
| 交换前校验 | 物品栏空位够；石币不超过持有、收到后不超过携带上限（统一 1000 万，`battle.MaxHaveGold`）；宠物栏有空位；掉地即消失的物品（`VANISHATDROP`）不能交易；收到的宠物比自己高 5 级以上且自己没转生过不能收；家族守护兽不能交易；骑乘中的宠物不能交易；同一个格子报了两次（洗物品）直接失败 | `TRADE_CheckItembuf` |
| 宠物过户 | 出战宠物先取消出战；换主人和主人账号（`OWNERCDKEY`、`OWNERCHARANAME`）；重算数值；放生计时清零 | `TRADE_ChangeItem` 的 `P/P` 分支 |
| 失败 | 任何一项不通过：双方窗口关闭，各收到一句原因（“X 物品栏已满”“X 钱不够”等），不换任何东西 | `TRADE_SwapItem` |
| 日志 | 成功后写 `trade.log`：双方账号、角色名、物品编号和唯一码、石币、宠物名和等级 | `LogTrade` |
| 取消 | 任何一方发 `TD|W` 关闭，对方收到“X 将交易取消了！” | `TRADE_Close` |

**原版的毛病**（新设计要避开，不照搬）：

1. 双方各自把“最后的报价”由客户端发来，服务端拿两份比对，数字和格子编号都信客户端发的，是外挂复制物品、石币的老入口。新设计报价存在**服务端**，客户端只说“把报价设成这样”，锁定和确定都只带版本号。
2. 对方在你锁定之后改报价，你的锁定**不会被撤销**，可以被“先看你锁定、再偷换”。新设计：任何一方改报价，双方的锁定和确定一起清零。
3. 交换不是事务：背包、宠物、石币逐步修改，中途出错会留下半截状态。新设计：一个数据库事务。
4. 没有超时：一方挂机，另一方一直被占着。新设计：邀请 30 秒过期，交易窗口 5 分钟没有任何操作自动取消。
5. 没有“同意”这一步，任何人走到面前就能给你弹一个窗口。新设计：和组队一样先发邀请，对方同意才开窗。

## 二、规则

### 2.1 总表

| 规则 | 说明 |
|---|---|
| 范围 | 双方都在世界中、**同一张地图**（沿用“附近玩家”，没有手动走路，原版的“面对面”对应成同图）。交易开始后双方位置不会变（见 2.5），所以不再检查同图 |
| 人数 | 一次一对一；一个角色同一时间只能有一笔进行中的交易；待处理的交易请求有数量上限（见 2.2） |
| 谁能交易 | 没倒下、不在战斗中、**不在真人队里**（原版：组队中不能交易）。分身队不限制（分身不是真人，不会被带入战斗） |
| 交易开关 | 角色自己的设置 `trade`，默认开。关掉后别人邀请回复 `TARGET_REFUSES`，自己仍可主动邀请别人（同 `invite` 开关的语义，见 5.69）。**需要加字段**（见 4.1） |
| 报价 | 每方：**物品最多 2 格（整格，含全部数量）+ 石币 + 宠物最多 1 只**，都可以为空，也可以只有一方出东西（赠送）。和原版的差别：石币不再占用物品位（原版 2 个位置里放了石币就只能再放 1 件物品），是对原版的放宽，见“待拍板”第 2 条 |
| 不能放进报价的东西 | 装备格（0–4）上穿着的物品；`VANISHATDROP` 的物品（原版“丢在地上会消失的物品无法交易”）；骑乘中的宠物（`PET_RIDING`）；家族守护兽（家族还没做，做家族时补）。其余都可以，包括任务物品、耐久受损的装备、转生过的宠物 |
| 二步确认 | 编辑 → **锁定** → 双方都锁定后 → **确定** → 双方都确定后才交换 |
| 任何修改都清零 | 报价变化、一方取消锁定，都把双方的“已锁定”“已确定”全部清除，回到编辑阶段，对方的界面要有醒目的“对方修改了报价”提示 |
| 取消 | 任何一方随时可以取消，整笔作废；对方离开世界、断线、被 agent 抢走控制权也算取消。**不保留座位**，断线重连后交易不恢复（同 `reconnect.md`） |
| 超时 | 邀请 30 秒；交易窗口 5 分钟内双方都没有任何交易操作则自动取消。到期由服务端定时器统一扫描 |
| 交易中的限制 | 参与者除聊天（`chat`）和查看类请求外，所有操作类请求回复 `IN_TRADE`（`message` 写“交易中，先完成或取消交易”）。这样背包、宠物、石币在交易期间不会被自己改掉；服务端交换前仍然重新校验一遍（管理命令发放物品之类的外部改动） |

### 2.2 邀请与同意

沿用组队请求的机制（`protocol.md` 5.67），请求的 id、过期、频率、对象上限、撤回都一样，请求类型换成 `trade`。**邀请被接受后，请求变成交易，id 沿用**。

- 有效期 30 秒；同一对 (发起人, 对象) 同时只有一条待处理请求（`REQUEST_PENDING`）；每个角色最多同时收 5 条交易请求（`TARGET_BUSY`）；同一发起人对同一对象 10 秒内最多发一次（`RATE_LIMITED`，带 `retry_after_seconds`）。
- **发起校验顺序**（第一个不满足的回复对应错误码）：功能开关 → 控制权 → 自己倒下（`CHARACTER_DEAD`）→ 自己战斗中（`IN_BATTLE`）→ 自己已在交易中（`IN_TRADE`）→ 自己在真人队里（`ALREADY_IN_PARTY`）→ 对方存在、在线且可见（`PLAYER_NOT_FOUND`，隐身者视同不存在）→ 同图（`PLAYER_NOT_NEARBY`）→ 不是自己（`INVALID_TARGET`）→ 对方关闭了交易（`TARGET_REFUSES`）→ 对方战斗中（`TARGET_IN_BATTLE`）→ 对方在真人队里（`TARGET_IN_PARTY`）→ 对方已在交易中（`TARGET_IN_TRADE`）→ 同一对已有请求（`REQUEST_PENDING`）→ 对方请求已满（`TARGET_BUSY`）→ 频率（`RATE_LIMITED`）。
- **答复** `accept: true` 时重新校验：发起人还在线（否则 `PLAYER_NOT_FOUND`）、双方都不在战斗中、不在交易中、不在真人队里、都没倒下。通过后：双方开着的 NPC 窗口先推 `npc_window_closed`；该双方其他待处理的交易请求全部作废（`cancelled`）；交易建立。校验失败则请求作废，发起人收到 `trade_request_result`（`cancelled`，带 `code`）。
- 拒绝不说明原因，发起人收到 `declined`。

### 2.3 报价、锁定、确定（状态机）

每方有两个布尔值：`locked`（已锁定）和 `confirmed`（已确定）。交易有一个递增的版本号 `rev`，每次报价变化 +1。

```text
编辑中 ──A 锁定──▶ A 已锁定 ──B 也锁定──▶ 双方已锁定 ──A 确定──▶ A 已确定 ──B 也确定──▶ 交换（事务）
   ▲                  │                        │                        │
   └── 任何一方改报价 / 任何一方取消锁定 ───────┴────────────────────────┘（全部清零，rev 变化）
```

- **报价**（`trade_offer`）是整体替换：请求里给出的字段覆盖对应部分（`items` 给空数组就是清空），没给的字段不变。服务端逐项校验（格子存在且在 5–19、不重复、不是不可交易物品、石币不超过持有、宠物存在且不在骑乘），任何一项不过整条请求失败、报价不变。成功后 `rev` +1，双方的 `locked`、`confirmed` 清零，推 `trade_updated`。
- **锁定**（`trade_lock`）带当前 `rev`，不一致回复 `TRADE_STALE`（说明对方刚改了报价，请重新看）。锁定前服务端做一次**预演**：假设现在交换，双方的物品栏空位、宠物栏空位、石币上限、宠物等级差能不能通过，不能通过就拒绝锁定，错误码写明是谁的问题（见 2.6）。这样一般不会走到“双方都确定了才失败”。
- **取消锁定**（`trade_unlock`）：清自己的锁定，并清双方的确定。
- **确定**（`trade_confirm`）只在双方都已锁定后可用（否则 `WRONG_STATE`），同样带 `rev`。第二个确定的人触发交换。
- **交换失败**（预演后状态又变了，例如管理命令刚发走了东西）：交易**不关闭**，回到编辑阶段，`trade_updated` 带 `last_error`（`code` 加 `who`），失效的报价项被自动移除。对原版“失败就关窗口”的放宽，见“待拍板”第 5 条。
- 版本号的作用：保证“我确定的就是我看到的那份”。锁定和确定的请求都必须带上客户端当前看到的 `rev`。

### 2.4 交换（服务端，一个事务）

1. 取双方的角色互斥锁，**按角色 id 从小到大的顺序加锁**，避免互相死锁。
2. 重新读取（不信内存）双方背包物品、宠物、石币，全部按 2.6 的规则再校验一遍。
3. 一个数据库事务内完成：
   - 物品：把物品行的所属角色改成对方，放进对方**最前面的空背包格**（5–19，两件物品按报价顺序依次放）。物品行整体过户，不新建不复制，所以**耐久、受损等级、合成标记（`merged`）等随物品走的列原样保留**（`durability.md` 已要求交易时带上耐久三列）。
   - 石币：双方各自一次 `UPDATE`，数值在事务内重新计算，不使用客户端数字。
   - 宠物：宠物行的所属角色改成对方，放进对方**最前面的空宠物栏**，`state` 重置为 `rest`（出战、待命的先取消）；人物本身的“出战宠物”如果是这只，同时取消。宠物的起始快照（`origin_*`，成长率依据，STAGE-215）和技能、素质点、名字不变；忠诚由规则按新主人的等级和魅力现算，战斗里累积的可变部分（STAGE-127）保留。
   - 写一条交易日志（见 2.7）。
4. 提交成功后更新内存里的 `Presence`，再按下面的顺序推送：先 `inventory_changed`、`pets_changed`（双方都推，石币在 `inventory_changed.gold` 里），再 `trade_ended`（`status: completed`），最后双方消息栏的“交易 OK”。
5. 事务失败（数据库错误）：回滚，交易取消，两边收到 `trade_ended`（`cancelled`，`code: INTERNAL_ERROR`），内存不变。

### 2.5 交易期间的世界

- 位置冻结：交易中 `warp`、`use_exit`、`encounter_start`、`leveling_start`、`pet_encounter_start` 等一律 `IN_TRADE`，所以不会出现“交易中途被带进战斗”。
- 组队类请求（`party_invite`、`party_join`、`party_reply` 的接受等）在交易中也回复 `IN_TRADE`；别人邀请交易中的人组队回复 `TARGET_IN_TRADE`（组队校验里新增这一项，放在 `TARGET_IN_BATTLE` 之后）。
- 离开世界、断线（所有连接都断开，同账号 agent 连接还在线不算）、被另一端抢控制权（见 2.9）：交易取消，对方收到 `trade_ended`。
- 服务重启：交易只存内存，全部消失（和组队请求一致）。

### 2.6 校验规则与错误码

交换前（预演、锁定、确定、实际交换）统一走同一个函数，保证任何一处通过就等于能交换。

| 检查 | 规则 | 错误码 | 原版 |
|---|---|---|---|
| 物品存在 | 报价格仍有同一件物品（按物品行 id，不按格号），不是装备格 | `EMPTY_SLOT`（报价时）；交换时被移走则自动从报价中移除 | `TRADE_HandleItem` |
| 不可交易物品 | `VANISHATDROP` 为 1 | `ITEM_UNTRADABLE`（新增） | `-12` |
| 石币够 | 报价 ≤ 持有；0 允许 | `NOT_ENOUGH_GOLD` | `-5 / -7` |
| 石币上限 | 收到后不超过接收方携带上限，**用背包实际用的上限**（见“待拍板”第 6 条） | `GOLD_FULL` | `-4 / -6 / -8 / -9` |
| 背包空位 | 接收方空格数 ≥ 收到的物品数减去自己给出去而腾出的格数（互换时各腾出的格子算进去） | `BAG_FULL` | `-2 / -3` |
| 宠物栏空位 | 接收方有空栏位，或自己同时交出一只宠物（互换） | `PET_FULL`（新增，原版只是一句提示） | `-10 / -11` |
| 宠物不能骑乘中 | 报价的宠物是骑乘宠物 | `PET_RIDING`（已有） | `-1` |
| 守护兽 | 家族守护兽不能交易 | `PET_UNTRADABLE`（新增，和家族一起做） | `-15` |
| 宠物等级差 | 接收方宠物等级 − 人物等级 > 5，且接收方未转生过：不能收 | `PET_TOO_STRONG`（新增，说明里写明“X 等级不够，无法照顾交易后的宠物”） | `-13 / -14` |
| 同格重复 | 报价里同一个格子出现两次 | `BAD_REQUEST` | `itemindex1==itemindex2` |

错误说明里的“谁”用 `error.data.who` 给出（`"me"` 或 `"peer"`），客户端据此把“你的背包满了”和“对方的背包满了”分开显示；对方的物品栏满了这种信息**不泄露具体格子数**，只说“对方物品栏已满”。对方的石币超上限（`GOLD_FULL`，`who` 为 `"peer"`）说“对方石币已达上限”，不说物品栏（STAGE-294）。

### 2.7 日志与审计

原版 `trade.log` 是文本文件；新服务端写数据库表 `trade_logs`（迁移见 4.1），一笔成功交易一行：

| 列 | 内容 |
|---|---|
| `id`、`created_at` | 交易 id（`t-N` 的数字部分加数据库序列）和成交时间 |
| `a_char_id`、`b_char_id`、`a_name`、`b_name`、`a_account`、`b_account` | 双方（名字当时快照，以后改名不影响） |
| `a_gold`、`b_gold` | 各自付出的石币 |
| `a_items`、`b_items` | JSON：物品行 id、物品模板编号、名字、数量、耐久 |
| `a_pet`、`b_pet` | JSON：宠物行 id、种族、名字、等级、转生次数、素质点（便于追查复制或倒卖） |

取消的交易不写表，只在服务端文本日志里留一行（和协议日志同一套）。agent 参与的交易，日志里多记一个标记（`via_agent`），审计规则同 `protocol.md` 9.6。

### 2.8 和现有系统的关系

| 系统 | 关系 |
|---|---|
| 真人组队（5.67） | 在真人队里不能交易（原版规则）；分身队不限制；交易中不能组队 |
| 社交开关（5.69） | 新增第三个开关 `trade`（默认开）。隐身者不能被按名字邀请交易（`PLAYER_NOT_FOUND`） |
| 战斗 | 倒下和战斗中不能发起、不能答复；战斗开始时不会有交易（交易中不能遇敌） |
| NPC 窗口 | 接受交易时关闭双方的 NPC 窗口；交易中不能开 NPC 窗口（`IN_TRADE`） |
| 骑乘 | 骑着的宠物不能交易；骑乘的人可以交易别的宠物 |
| 装备耐久（`durability.md`） | 物品行过户，耐久列随物品走；对方能看到耐久（见 3.2 的物品对象） |
| 宠物成长（STAGE-215/216） | 起始快照不变，成长率仍按“从获得时起”计算；`growth.basis` 对买到的宠物保持原值（不当成 `caught`），见“待拍板”第 4 条旁注 |
| 断线重连（`reconnect.md`） | 旧交易作废，不恢复，已经写好 |
| agent（`agent.md`） | 见 2.9 |

### 2.9 agent

- 玩家连接和 agent 连接都能发交易请求；观察方和被操控的角色按 `CONTROLLED_BY_AGENT` / `CONTROLLED_BY_PLAYER` 拦截（和组队一样，`protocol.md` 9.3）。
- 分身没有账号，不能被邀请交易，也不能邀请。
- 交易中途控制权被抢走（`take`、`release`、agent 登录）：**交易取消**，对方收到 `trade_ended`（`cancelled`，`code: CONTROL_CHANGED`）。不转交，避免 agent 接手一场自己没看过报价的交易。
- **先问玩家分级**（`agent-guide.md` 第 6 节，新增请求必须登记，`go test ./server/webpages` 会检查）：

  | 级别 | 做法 | 请求 |
  |---|---|---|
  | 第一级 | 自己做，不用汇报 | `trade_reply` 的 `accept: false`、`trade_cancel`（撤回或取消）、`trade_unlock`（取消锁定，更保守） |
  | 第二级 | 做完汇报 | `trade_invite`（只是发邀请）、`trade_reply` 的 `accept: true`（只开窗，不转移东西）、`trade_offer`（可随时撤销，没有锁定前什么也不会发生） |
  | 第三级 | **必须先问，等玩家回复再做** | `trade_lock`（把报价定下来）、`trade_confirm`（真正成交，不可逆） |

  agent 手册同时要写一句：**对方改了报价（`trade_updated` 里 `rev` 变了），必须重新看，不能沿用旧的玩家许可**。

## 三、协议草案

接在 `protocol.md` 5.71 之后，暂定 **5.72**（编号以合并时为准）。请求都是操作类、世界中；协议版本号不变，只追加消息类型。

### 3.1 配置

服务端配置 `trade.enabled`，默认 `false`（做法同 `party.players_enabled`，位置见 `docs/server.md`）。关闭时下面所有请求回复 `WRONG_STATE`（`message` 写“交易尚未开放”），不推送。客户端和服务端都做完、一起进测试之后再打开。

### 3.2 请求

| 请求 | data | 谁能发 | 成功回复 |
|---|---|---|---|
| `trade_invite` | `{"name": 对方角色名}` | 没有交易、没有真人队者 | `{"request": 请求对象}` |
| `trade_reply` | `{"id": "t-17", "accept": true/false}` | 请求的对象 | 接受：`{"trade": 交易对象}`；拒绝：`{}` |
| `trade_cancel` | `{"id": "t-17"}` | 发起人（请求阶段），或参与者（交易阶段） | `{}` |
| `trade_offer` | `{"id": "t-17", "items": [5, 8], "gold": 5000, "pet": 2}` | 参与者 | `{"trade": 交易对象}` |
| `trade_lock` | `{"id": "t-17", "rev": 4}` | 参与者 | `{"trade": 交易对象}` |
| `trade_unlock` | `{"id": "t-17"}` | 参与者 | `{"trade": 交易对象}` |
| `trade_confirm` | `{"id": "t-17", "rev": 4}` | 参与者（双方已锁定） | 第一个确定：`{"trade": 交易对象}`；第二个确定：`{"done": true}` |

```jsonc
{"id": 90, "type": "trade_invite", "data": {"name": "路人乙"}}
{"id": 90, "type": "trade_invite", "ok": true, "data": {"request": {"id": "t-17", "from": "勇者小明", "to": "路人乙", "expires_in": 30}}}

{"id": 91, "type": "trade_offer", "data": {"id": "t-17", "items": [5], "gold": 5000, "pet": null}}
{"id": 91, "type": "trade_offer", "ok": true, "data": {"trade": {
  "id": "t-17", "rev": 2, "idle_expires_in": 300,
  "me":   {"name": "勇者小明", "items": [{"slot": 5, "item_id": 20, "name": "小斧头", "effect": "攻 +9 防 -3 敏 -3", "count": 1, "durability": 80, "max_durability": 100, "crush_level": 0}],
           "gold": 5000, "pet": null, "locked": false, "confirmed": false},
  "peer": {"name": "路人乙", "items": [], "gold": 0, "pet": null, "locked": false, "confirmed": false},
  "last_error": null}}}
```

- `trade_offer` 的字段：`items`（背包格号数组，最多 2 个，元素是 5–19 的整数且不能重复）、`gold`（非负整数，0 = 不出）、`pet`（宠物栏位 0–19，`null` = 不出）。三个字段都可以省略，省略的不改；其他字段回复 `BAD_REQUEST`（拼错字段名不静默失效）。
- 对方的物品条目**没有 `slot`**（那是对方的背包格号，与你无关），其余字段与 `inventory` 的物品条目相同。对方的宠物条目是 `pets` 里的宠物条目去掉 `slot` 和 `state`，所以买方能看到素质点档位、成长率和技能（见“待拍板”第 4 条）。
- `trade_confirm` 的响应：第一个确定的人收到的 `trade` 里 `me.confirmed` 为 `true`；第二个确定会触发交换，响应是 `{"done": true}`，随后的推送顺序见 2.4。交换失败回到编辑阶段时，响应是 `{"trade": 交易对象}`，`last_error` 非空。

### 3.3 推送

- `trade_request`：只推给对象在世界中的每条连接，`data` 为 `{"request": 请求对象}`，请求对象多一个 `from_level`、`from_transmigration`（让对方判断是不是新手号）。
- `trade_request_result`：`data` 为 `{"id", "status", "from", "to"}`，`status` 同组队：`accepted`（发起人收到，紧接着收到 `trade_updated`）、`declined`、`expired`、`cancelled`（带 `code` 时说明原因）。
- `trade_updated`：交易对象有任何变化（建立、对方改报价、对方锁定或取消锁定、对方确定、交换失败回到编辑）时推给**对方**的所有连接，`data` 为 `{"trade": 交易对象}`（`me` 和 `peer` 已经按接收者的视角换好）。自己的操作靠响应拿到，不推给自己。
- `trade_ended`：交易结束时推给双方（包括发起结束的人），`data` 为 `{"id", "status": "completed" | "cancelled", "by": 角色名 | null, "code": 取消原因 | null, "summary": 摘要}`。`code` 取值：`CANCELLED`（对方点了取消）、`PEER_LEFT`（离开世界或断线）、`TIMEOUT`、`CONTROL_CHANGED`、`INTERNAL_ERROR`。`summary` 只在 `completed` 时有，`{"gave": {...}, "got": {...}}`，结构同报价里的 `items`、`gold`、`pet`，方便消息栏和日志显示。两方各收到**自己视角**的摘要：`gave` 是自己给出的，`got` 是自己拿到的（STAGE-294：甲出 300、乙出 200，甲的 `got` 是 200，乙的 `got` 是 300）。
- 推送可能丢失或晚到：客户端在重连后丢弃交易状态；交易中收到 `trade_updated` 的 `rev` 比本地小的忽略。

### 3.4 `status` 与 `enter_world`

`enter_world`、`status` 的响应带 `trade: null`（正在交易时是交易对象，进入世界时总是 `null`，因为断线即取消）。`social` 对象多一个 `trade` 字段（`{"visible", "invite", "trade"}`）；`social_settings` 请求新增可选字段 `trade`（布尔），其余规则同 5.69。

### 3.5 新增错误码

| 错误码 | 含义 |
|---|---|
| `IN_TRADE` | 自己交易中，不能做这件事；或自己要发起交易时已经在交易中 |
| `TARGET_IN_TRADE` | 对方已在交易中 |
| `TRADE_NOT_FOUND` | 交易不存在、已结束，或不是你的（请求阶段沿用 `REQUEST_NOT_FOUND`） |
| `TRADE_STALE` | `rev` 与当前不一致（对方刚改了报价） |
| `ITEM_UNTRADABLE` | 物品不能交易 |
| `PET_UNTRADABLE` | 宠物不能交易（守护兽） |
| `PET_FULL` | 宠物栏已满 |
| `PET_TOO_STRONG` | 宠物比接收方高太多级，收不了 |

沿用：`WRONG_STATE`、`BAD_REQUEST`、`PLAYER_NOT_FOUND`、`PLAYER_NOT_NEARBY`、`INVALID_TARGET`、`TARGET_REFUSES`、`TARGET_IN_BATTLE`、`TARGET_IN_PARTY`、`TARGET_BUSY`、`REQUEST_NOT_FOUND`、`REQUEST_PENDING`、`RATE_LIMITED`、`CHARACTER_DEAD`、`IN_BATTLE`、`ALREADY_IN_PARTY`、`EMPTY_SLOT`、`NOT_ENOUGH_GOLD`、`GOLD_FULL`、`BAG_FULL`、`PET_RIDING`、`CONTROLLED_BY_AGENT`、`CONTROLLED_BY_PLAYER`。

## 四、服务端实现要点

### 4.1 存储

- 迁移（编号以合并时为准，注意和 test 上别的需求撞号，见 `migration-number-collision-on-test`）：
  - `characters` 加 `social_trade boolean not null default true`。
  - 新表 `trade_logs`（见 2.7）。
- 交易本身和请求只放内存（`World` 里一张表，键是交易 id，每个角色指向自己的交易），不入库。

### 4.2 代码位置（建议）

`server/character/` 下按职责拆文件，避免超 500 行：

- `trade.go`：交易对象、注册表、状态机、定时扫描。
- `trade_request.go`：邀请、答复、撤回（尽量复用组队请求的生成、过期、频率限制代码，不要复制第二份）。
- `trade_offer.go`：报价校验。
- `trade_exec.go`：预演与事务交换（2.4 的步骤，物品/宠物/石币各一个小函数）。
- `trade_push.go`：推送。
- 拦截：在操作类请求的统一入口加一条 `IN_TRADE` 检查，不在每个处理函数里各写一遍（参照 `PARTY_FOLLOWER` 的拦截点）。

### 4.3 测试

协议用例（`docs/protocol/cases/`，`server/casetest` 回放，两个账号）：

| 用例 | 内容 |
|---|---|
| `trade_basic` | 邀请、接受、报价、锁定、确定，核对双方背包、宠物栏、石币和推送顺序 |
| `trade_gift` | 只有一方出东西（赠送） |
| `trade_decline_cancel` | 拒绝、撤回、过期、取消 |

## 五、界面

依据 `docs/ui.md`、`docs/interaction.md`：ratatui 经典 demo 风格，16 色具名颜色，`--unicode false` 时降级。

### 5.1 入口

- **场景页「附近玩家」列**：`Enter` 的动作面板新增「交易」（`social-players.md` 1.3 的动作表）。条件：自己和对方都没倒下、不在战斗、不在真人队、不在交易中，对方没关交易。不满足仍显示但灰掉，`Enter` 只在消息栏说明原因，不发请求。
- **命令**（`client/src/app/trade.rs`，菜单和命令共用同一批函数）：

  | 命令 | 别名 | 含义 |
  |---|---|---|
  | `trade 名字` | `交易` | 邀请 |
  | `trade accept [名字]` | `同意` | 同意收到的交易请求，规则同 `party accept` |
  | `trade decline [名字]` | `拒绝` | 拒绝 |
  | `trade cancel` | `取消` | 请求阶段撤回，交易阶段取消（交易窗口里等价于 `Esc` 的取消） |

  交易窗口里的锁定和确定不做命令（避免误敲），只有窗口里的按钮；agent 用请求。
- **收到邀请**：和组队邀请共用同一个确认弹窗和排队规则（`social-players.md` 2.8）：

  ```text
  ┌ 交易邀请 ─────────────────────┐
  │ 阿牛（Lv30，转生 1）想和你交易 │
  │ 剩余 23 秒                     │
  │        [拒绝]    [同意]        │
  └───────────────────────────────┘
  ```

  默认焦点在「拒绝」，`←→` 切，`Enter` 激活，`Esc` = 稍后处理。社交页的「请求」栏同时列出组队请求和交易请求，行首标记区分（`队` / `易`）。战斗中和 NPC 窗口里不弹，只在消息栏提示。

### 5.2 交易窗口

交易建立后，整屏居中弹出交易窗口（`Clear` + 弹窗，`ui.md` 769 行已写“交易进行中用弹窗显示双方报价”），不再响应场景页的按键：

```text
┌ 交易 · 路人乙（Lv12）──────────────── 剩余 4:32 ┐
│┌ 我的报价 ──────────────┐┌ 对方的报价 ─────────┐│
││ 物品 1  小斧头 x1      ││ 物品 1  回复药 x5   ││
││ 物品 2  （空）         ││ 物品 2  （空）      ││
││ 石币    5,000          ││ 石币    0           ││
││ 宠物    乌力 Lv5       ││ 宠物    （无）      ││
│└────────────────────────┘└─────────────────────┘│
│ 你：编辑中        对方：已锁定 ✓                  │
│ 对方改动了报价，双方锁定已取消                    │
│        [锁定]      [取消交易]                     │
└──────────────────────────────────────────────────┘
 ↑↓ 选择 · Enter 修改/确认 · Esc 取消交易
```

- **面板**：左右两块 `Block::bordered()`，标题「我的报价」Cyan、「对方的报价」Magenta（加粗）；各四行（物品 1、物品 2、石币、宠物）。底部状态行用 `Gauge` 风格的三态标记：编辑中（White）、已锁定（Yellow）、已确定（Green）。
- **焦点**：`↑↓` 在“我的报价”四行和底部按钮间移动；`←→` 在底部按钮间切换。对方面板只读，不可聚焦。`Tab` 打开焦点行物品或对方宠物的详情（效果文字、耐久，宠物的素质档位、成长率、技能）。
- **修改报价**：
  - 物品行 `Enter`：弹出我的背包选择列表（只列 5–19 格里能交易的物品，已经在另一行的灰掉）；选中一项放入，再选「清空」移除。
  - 石币行 `Enter`：弹出**专用数字输入表单**（普通字符只在专用表单里接收，符合 `interaction.md`），`Enter` 提交，`Esc` 取消；超过持有量时本地先提示、不发请求。
  - 宠物行 `Enter`：弹出宠物选择列表（骑乘中的灰掉并写原因）。
  - 每次修改发一次 `trade_offer`（整体替换：把当前窗口里的三项一起发）。
- **按钮**：`[锁定]` → 变成 `[取消锁定]`；双方都锁定后出现 `[确定]`（Green 加粗），按下后变成「等待对方确定…」。`[取消交易]` 永远在。按钮遵守 `interaction.md` 的“默认取消”：窗口打开、对方改了报价、锁定状态每次变化后，焦点都自动回到 `[取消交易]`，防止对方在你按下 `Enter` 的瞬间改报价，导致误锁定、误确定。
- **对方改报价的提示**：状态行第二行 Yellow 显示「对方修改了报价，双方锁定已取消」，同时对方面板里**变了的行**前加 `●` 标记，直到我下一次按键。消息栏同步写一行。
- **`Esc`**：报价为空且没人锁定时直接取消；否则弹确认「取消这笔交易？」默认选「继续交易」（规则见 `interaction.md`「确认」）。
- **交易结束**：窗口关闭，消息栏写结果：

  | 场景 | 消息栏（颜色） |
  |---|---|
  | 成交 | 交易 OK！获得：…；付出：…（Green） |
  | 对方取消 | 路人乙将交易取消了！（Yellow） |
  | 对方离开 | 路人乙已离开，交易取消（Yellow） |
  | 超时 | 交易超时，已取消（Yellow） |
  | 锁定时被预演拒绝 | 路人乙物品栏已满，请整理后再交易 / 你物品栏已满，请整理后再交易（Red） |
  | 宠物等级差 | 你等级不够，无法照顾交易后的宠物！（Red） |
  | 石币超限 | 你的石币将会超过上限！（Red） |
  | 不可交易 | 丢在地上会消失的物品无法交易！（Red） |
  | 拒绝 / 过期 | 路人乙拒绝了交易 / 交易邀请已过期（Yellow） |
  | 对方关了交易 | 对方不愿意跟你交易！（Yellow） |

  这些文字沿用原版的口气（出处 `trade.c` 文件头的 `TRADE_*` 常量），并把原版的“物品栏已满，请整理後再交易～”等改成新界面的措辞。
- **断线与重连**：窗口立刻关闭，消息栏写「连接断开，交易已取消」，重连后不恢复（`reconnect.md`）。
- **观察方**（agent 操控时）：窗口不弹；收到邀请时只在消息栏写「路人乙想和你交易（agent 正在操控）」。若在交易中途被 agent 抢走控制权，窗口关闭并写「交易因控制权变化取消」。

### 5.3 社交页的开关

「社交开关」栏（`ui.md`“社交页的开关”）加第三项「接收交易邀请」，默认开，行为同另外两项（立即生效，`social_settings` 的 `trade` 字段）。

### 5.4 验收（界面）

- 80×24 下交易窗口完整显示，宠物名、物品名过长按终端宽度截断，数量和石币必须保留。

下面几条我已按推荐值写进上文，不同意的话改的地方都集中在对应小节：

1. **交易要不要先发邀请、对方同意才开窗**（2.2）。推荐：要。原版是对方交易开关开着就直接开窗，对方没有拒绝的机会；新设计的邀请机制已经做好，复用成本低。
2. **石币是否单独于两个物品位之外**（2.1）。推荐：单独，即 2 件物品 + 石币 + 1 只宠物。原版是 2 个位置里物品、石币二选一。要完全照搬就改成“最多 2 项，每项物品或石币”。
3. **真人队里不能交易**（2.1，原版规则）。推荐：照原版；放开的话，队长一遇敌就要处理队员的交易，复杂度不小。分身队不限制。
4. **对方能看到宠物的完整资料**（素质档位、成长率、技能，3.2）。推荐：给，买卖宠物不看这些等于盲买；原版只给等级、攻防敏、血上限、转生次数。*旁注*：买到的宠物起始快照保持不变，成长率仍按“养大时”的口径算，不会因为换了主人就从 0 起算。
5. **交换失败时交易回到编辑而不是直接关闭**（2.3）。推荐：回到编辑，被拒的一方整理背包后重新锁定即可，不必重新邀请；原版是关窗重来。
6. **石币携带上限（已拍板：统一 1000 万）**：固定值，不随转生变化。商店、交易、战斗拾取和偷取、管理命令发石币共用 `battle.MaxHaveGold`（10_000_000），原先的 `shop.go` 的 `MaxGold` 和 `battle/rewards.go` 的 `1000000 + 转生 × 1800000` 已删除。不再沿用原版 `CHAR_getMaxHaveGold` 的 `_FIX_MAX_GOLD` 公式。（STAGE-310 落地）
7. **不做新手号限制**。原版没有等级门槛；先不做，靠 `trade_logs` 事后追查。如果担心小号倒货，可以以后加“等级 ≥ N 才能交易”，错误码用 `REQUIREMENT_NOT_MET`。
8. **每次只能整格交易**（含全部数量）。原版就是整格；拆开数量交易要再加 `count` 字段，推荐等有需求再做。
